## 맵 크기 변경 이력

| 시점 | 크기 | 이유 |
|---|---|---|
| P1 | 50.7 × 28.5 (한 화면의 9배 면적) | 컨셉의 "현재 전체화면의 9배" |
| 2026-09-05 | **76.05 × 42.75** (각 변 1.5배 = 20.25배 면적) | 운동장(트랙+축구장)이 가운데를 차지해 걸어 다닐 곳이 좁아짐. **운동장 절대 크기는 그대로 두고 섬만 키웠다** — 함께 키우면 비율이 같아 문제가 해결되지 않는다 |

맵을 또 키울 때: `data/world.json`의 `size_x/size_z`만 고치면 클라이언트·서버 경계가 함께 바뀐다. 다만 바위·채집물 좌표는 자동으로 퍼지지 않으므로 함께 늘려야 하고, 늘린 뒤 **운동장과 겹치는지** 확인해야 한다(트랙 안에 바위가 있으면 자전거로 지나갈 수 없다).

## 확장 지점 (컨셉의 "확장 가능"을 어디서 지키는가)

| 확장 대상 | 어디를 고치면 되는가 |
|---|---|
| 캐릭터 프리셋 수(5 → N) | `data/characters.json`에 항목 추가. UI는 개수를 읽어 배치한다 |
| 월드맵 크기(9배 → N배) | `data/world.json`의 `size_x`/`size_z`. 서버 클램프도 같은 파일을 읽는다 |
| 모임 존 | `data/world.json`의 `zones[]` |
| 이모티콘 | `data/emotes.json` |
| 아이템·가격 | `data/items.json` |
| 색 | `data/palette.json` |

**원칙**: "확장 가능"은 코드를 고치지 않고 `data/*.json`만 고쳐서 되는 상태를 뜻한다. 데이터에 없는 값을 코드가 하드코딩하면 그 확장 지점은 거짓말이 된다 — `tests/test_palette.gd`가 색에 대해 하는 검사를 다른 데이터에도 같은 방식으로 붙여 나간다.

## P1~P4에서 실측으로 드러난 것 (다음 단계에 영향)

- **한글 입력**: Playwright 합성 키 이벤트로는 Godot 웹에 한글이 입력되지 않는다(IME 조합 이벤트 필요). 자동 테스트는 ASCII로 파이프라인만 검증하고, 한글 이름·채팅은 사람이 확인해야 한다. 실제 사용자 입력은 브라우저 IME를 타므로 문제없을 것으로 보이지만 **아직 사람이 확인하지 않았다**.
- **테스트 판정의 함정**: 스크린샷 해시 변화로 판정하면 실패한 동작도 토스트 때문에 화면이 변해 거짓 통과한다(실제로 줍기 실패를 통과로 봤다). 그래서 2탭 테스트는 Node WS 옵저버가 받은 브로드캐스트로 판정한다.
- **가방의 단일 출처**: 채집(클라이언트)과 드랍/줍기(서버 권위)가 다른 가방을 보면 드랍이 항상 거부된다. `gather` 메시지로 서버를 단일 출처로 만들었다.
- **이름표 표시 순서**: 트리에 이미 붙은 노드는 `ready`가 즉시 지나가므로 시그널로 이름을 넣으면 내 이름표만 비어 있었다. 값을 들고 있다가 `_ready`에서 적용하는 방식으로 고쳤다.

## 알려진 버그 / 부채 (발견 순)

### 🟡 2탭 테스트의 석벽 우회 검증이 간헐 실패한다

기능은 정상이지만(여러 번 통과 확인) 검증이 **위치·카메라 타이밍에 취약**하다: 석벽 건너편 지점이 화면 안에 들어와야 클릭할 수 있고, 앞 단계에서 A가 어디에 있는지에 따라 그 조건이 실행마다 달라진다. 접근·재시도·카메라 안정 대기를 넣어 크게 줄였지만 완전히 없애지는 못했다.

**고치는 방향**: 검증용으로 카메라를 잠깐 넓히는 테스트 훅(예: 카메라 size 강제)을 두거나, 우회 판정을 헤드리스(`tests/test_path.gd`)에만 맡기고 브라우저에서는 "벽을 통과하지 않는다"만 확인한다.

### 🔴 판매가 서버에 반영되지 않는다 (벨 무한 획득 경로)

`world.gd::_sell_all`은 **로컬 슬롯만** 갱신하고 서버에 알리지 않는다. 프로토콜에 판매·벨 개념 자체가 없어(`docs/protocol.md`) 서버 레코드에는 `inventory`만 있고 `bells`가 없다. 결과:

1. 판매 → 로컬 벨 증가, 로컬 가방 비움. **서버 가방은 그대로.**
2. 재접속 → `welcome`이 서버 가방으로 로컬을 덮어써(§4 우선순위) **판 물건이 되살아난다.**
3. 다시 판매 → 벨이 또 늘어난다. 반복 가능.

또한 벨이 서버에 없으므로 **다른 기기에서 같은 토큰으로 접속하면 벨이 0**이다.

**고치는 방향**: `sell` 메시지를 프로토콜에 추가하고 서버가 가방을 비우며 벨을 계산·보관한다(가격은 서버도 `data/items.json`을 읽으므로 클라이언트가 금액을 주장하지 않아도 된다). 벨을 서버 레코드에 넣으면 기기 간 이전도 자연히 해결된다.

## 알려진 제약

- **http로 열면 소리가 나지 않는다**(비보안 컨텍스트에 AudioWorklet이 없다). 사운드를 넣는 시점에 HTTPS가 사실상 필수가 된다 — `docs/deploy.md`의 "보안 컨텍스트" 절 참고.
- 엔진 wasm 9MB(brotli)는 Godot 웹 빌드의 고정 비용이다. 더 줄이려면 폰트 서브셋과 기능 축소 빌드가 필요하다.

## 운동장에서 남은 것

- **레인을 강제하지 않는다.** 자전거로 인라인 레인(빨강)을 달려도 막지 않는다. 색으로 구분만 하고 규칙은 두지 않았다 — 막으면 트랙 바깥으로 나가는 순간마다 조작이 튄다.
- **골 점수는 골대별 누적뿐이다.** 팀 개념이 없어 "누가 넣었는지"는 세지 않는다. 팀을 넣으려면 존 안에서 편을 나누는 UI가 먼저 필요하다(P5와 같은 문제).
- **공은 하나뿐이고 세이브에 남지 않는다.** 서버가 재시작하면 중앙에서 다시 시작한다.
- **줄넘기 기술은 모습만 다르다.** 성공/실패 판정이나 횟수 세기는 없다 — 그건 미니게임(P5)의 영역이다.

## 폰 조작에서 남은 것

- **조이스틱 영역(왼쪽 아래 절반)의 탭은 버려진다.** 그 영역은 플로팅 조이스틱이 쓰는데, 짧게 탭만 하면(끌지 않으면) 캐릭터가 움직이지 않는다. 그 자리에 있는 나무를 탭해도 아무 일이 없어서, 운동장이 섬 가운데를 차지한 뒤로 이 상황이 흔해졌다(2026-09-05 모바일 테스트에서 드러남). 지금은 "스틱 OFF"로 우회할 수 있다. 고치려면 **끌지 않고 뗀 짧은 터치는 탭-투-무브로 흘려보내야** 한다(TouchControls의 멀티터치 추적에서 드래그 임계값·시간으로 구분).

## 미해결 설계 질문

- **미니게임 판정(P5)**: 클라이언트 신뢰 모델(`docs/protocol.md` §3)로는 결과가 걸린 게임을 못 올린다. 존 안에서만 서버 권위로 돌릴지, 아니면 방장 클라이언트를 신뢰할지 결정 필요.
- **토큰 분실**: 브라우저 저장소를 지우면 캐릭터가 사라진다. 토큰 표시/입력 UI(P6) 전까지는 감수한다.
- **다각형 장애물의 내비게이션**: 원(바위)은 접선 계산으로 풀었지만, 건물·울타리처럼 다각형 장애물이 생기면 `NavigationServer3D` + 내비메시로 교체해야 한다.
- **서버가 바위를 모른다**: 조작된 클라이언트는 바위를 통과할 수 있다. 미니게임(P5)처럼 결과가 걸린 상호작용에서는 위치 검증을 서버로 옮겨야 한다.
- **한글 IME 실기 확인**: DOM 입력으로 바꿨지만 폰에서 실제로 한글이 조합되는지, 키보드가 올라올 때 입력창이 가리지 않는지는 아직 사람이 확인하지 않았다.
- **동시 접속 규모**: 현재 구조(전원에게 전체 브로드캐스트)는 수십 명 규모까지다. 그 이상이면 관심 영역(AOI) 분할이 필요하다.
