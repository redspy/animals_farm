# 실시간 프로토콜 (WebSocket)

## 0. 무엇을 왜 이렇게 정했나

멀티 기기 상호작용(다른 기기의 캐릭터가 같은 월드맵에 보이고, 채팅·이모티콘·아이템 드랍이 실시간으로 전달됨)을 위해 **서버 1개 + WebSocket JSON 메시지**로 간다.

- **Godot의 고수준 멀티플레이(ENetMultiplayerPeer)를 쓰지 않는 이유**: 웹 export는 UDP를 못 쓴다. WebSocketMultiplayerPeer도 있지만 그러면 서버도 Godot 프로세스여야 하고, 배포 서버는 이미 Node로 정적 파일을 서빙하고 있다. 프로세스를 하나로 유지하는 쪽이 배포·운영이 단순하다(`docs/deploy.md`).
- **의존성**: `ws`(npm) 하나만 추가한다. Node에는 WebSocket 서버 구현이 없고, RFC6455를 직접 구현할 이유는 없다. 정적 서버는 그대로 같은 프로세스·같은 포트에서 동작하고 `/ws` 업그레이드만 받는다.
- **신뢰 모델: 서버 권위 + 최소 검증**. 프로토타입이라 클라이언트가 보내는 좌표를 그대로 믿되(예측/보정 없음), 서버가 **월드 경계 클램프 · 이동 속도 상한 · 문자열 길이 · 레이트 리밋**만 강제한다. 아이템 드랍/줍기는 **중복 획득이 실제 손실로 이어지므로 서버가 소유권을 판정**한다. 이 선을 넘는 치팅 방지(권위적 시뮬레이션)는 범위 밖이며, 그 사실을 여기 남겨 "안전하다"고 오해하지 않게 한다.

## 1. 연결과 신원

```
클라이언트                                서버
  │  WS 연결: wss://<host>/ws               │
  ├────────────── join ────────────────────▶│  토큰으로 캐릭터 레코드 조회/생성
  │◀───────────── welcome ──────────────────┤  내 상태 + 월드 스냅샷
  │◀───────────── snapshot ─────────────────┤  현재 접속자·월드 아이템
```

- **토큰**: 캐릭터 슬롯을 처음 만들 때 클라이언트가 UUIDv4를 발급해 세이브(`user://save.json`)에 넣는다. 서버는 토큰을 키로 `{name, preset, pos, inventory}`를 보관한다. 즉 **토큰이 곧 신원**이고 계정·비밀번호는 없다.
- 그래서 **토큰을 아는 사람이 그 캐릭터다**. 브라우저 저장소를 지우면 캐릭터를 잃고, 토큰을 복사하면 다른 기기에서 같은 캐릭터로 접속할 수 있다(기기 간 이전 UI는 아직 없음 — 로드맵 P6).
- 이름은 표시용이며 **중복을 허용**한다. 슬롯이 기기별이므로 다른 기기에서 같은 이름·같은 외형이 존재할 수 있고, 이는 버그가 아니다.

### 같은 토큰으로 다시 들어올 때 (재접속)

폰은 화면이 꺼지거나 탭이 뒤로 가면 연결이 끊기고, 돌아오면 **같은 토큰으로 다시 `join`**한다. 이때 옛 소켓은 아직 서버에 열려 있을 수 있다.

- 서버는 새 소켓에 토큰을 넘기고 옛 소켓에 `error{code:'replaced'}`를 보낸 뒤 끊는다 — 한 캐릭터를 두 기기가 동시에 움직이면 위치가 튀고 어느 쪽이 진짜인지 정할 수 없다.
- **옛 소켓의 `close` 처리는 "지금 이 토큰의 연결이 나인가"를 먼저 확인해야 한다.** `close`는 다음 틱에 오므로 그때는 이미 새 소켓이 토큰을 갖고 있다. 확인하지 않으면 방금 들어온 **살아 있는 플레이어를 지우고** `leave`까지 알려서, 재접속한 사람은 자기 화면에 "서버 연결됨"인데 남들 화면에는 보이지 않고 접속자 바에도 없다(사용자 보고 "나갔다가 들어왔는데 보이지 않아", 2026-09-05). 회귀 판정은 `tests/server-reconnect.test.mjs`에 있다.

## 2. 메시지 형식

모든 메시지는 JSON 한 줄이며 `t`(type) 필드를 갖는다. 좌표는 월드 단위 float, 소수 2자리로 반올림해 보낸다(대역폭).

### 클라이언트 → 서버

| `t` | 필드 | 설명 |
|---|---|---|
| `join` | `token`, `name`, `preset` | 접속. 서버가 레코드를 만들거나 불러온다 |
| `activity` | `activity`, `trick` | 운동 시작/변경/그만두기(빈 문자열이면 그만두기). 줄넘기 기술은 `trick` |
| `kick` | `dx`, `dz` | 공 차기. 방향은 클라이언트가 정하고 **사거리·활동 상태는 서버가 검사한다** |
| `push` | `what`(`seesaw`/`carousel`) | 놀이기구 밀기. **타고 있는 사람만** 밀 수 있다 |
| `move` | `x`, `z`, `dir` | 내 위치·바라보는 방향(`"down"`\|`"up"`\|`"left"`\|`"right"`). 최대 10Hz |
| `chat` | `text` | 채팅(최대 200자). 초당 2건 |
| `emote` | `emote` | 감정 표현 키(`data/emotes.json`의 id). 초당 2건 |
| `gather` | `item` | 채집물을 캤다고 알린다(초당 4건). 서버는 채집물의 위치·재생 상태를 모르므로 **클라이언트 주장을 받아 적는다** — 이동 좌표와 같은 신뢰 수준이다. 그래도 서버가 가방의 단일 출처여야 한다: 그러지 않으면 채집(클라이언트)과 드랍/줍기(서버 권위)가 서로 다른 가방을 보게 되고, 실제로 드랍이 항상 "가방에 없는 아이템"으로 거부됐다(2026-09-04 2탭 실측에서 발견) |
| `sell` | `item`(선택) | 판매. `item`을 주면 그것만, 없으면 팔 수 있는 것 전부. **금액은 서버가 `data/items.json` 가격으로 직접 계산**한다 — 클라이언트가 금액을 주장하면 벨을 임의로 불릴 수 있다. 초당 2.5건 |
| `drop` | `item`, `x`, `z` | 인벤토리에서 1개를 월드에 놓는다 |
| `pickup` | `id` | 월드 아이템 id를 줍는다(서버가 소유권 판정) |
| `rename` | `name` | 이름 변경(최대 12자) |
| `resync` | — | **창 복귀 후 상태 재수신.** 다른 탭/앱에 갔다 오면 브라우저가 프레임을 멈춰 클라이언트 상태(내 위치·남의 위치·월드 아이템·채집물 재생 시각)가 굳는다. 재연결 없이 `welcome`(resync=true) + `snapshot`을 다시 받는다 |

### 서버 → 클라이언트

| `t` | 필드 | 설명 |
|---|---|---|
| `welcome` | `you`, `world` | 내 캐릭터 상태(위치·인벤토리 포함)와 월드 설정 |
| `snapshot` | `players[]`, `items[]` | 접속 직후 전체 상태 |
| `join` | `player` | 다른 캐릭터 접속 |
| `leave` | `token` | 다른 캐릭터 퇴장 |
| `move` | `moves[]` | 위치 갱신 묶음(서버 tick 10Hz, 변한 것만) |
| `chat` | `token`, `name`, `text`, `at` | 채팅 브로드캐스트 |
| `emote` | `token`, `emote` | 이모티콘 브로드캐스트 |
| `item_add` | `item` | 월드에 아이템이 놓임 |
| `item_remove` | `id`, `by` | 아이템이 사라짐(누가 주웠는지) |
| `inventory` | `inventory` | 내 인벤토리 갱신(채집/드랍/줍기 결과) |
| `sold` | `sold`, `total`, `bells`, `inventory`, `unsold` | 판매 결과. `bells`는 서버가 보관하는 최종 값 |
| `rename` | `token`, `name` | 이름 변경 브로드캐스트 |
| `activity` | `token`, `activity`, `trick` | 운동 상태 브로드캐스트 — 남의 화면에도 같은 모습이 보여야 하므로 서버를 거친다 |
| `ball` | `ball` (`{x, z, score}` 또는 `null`) | 축구공. `null`이면 아무도 축구를 하지 않아 공이 없다. **멈춘 공은 다시 보내지 않는다** — 정지 상태를 10Hz로 알릴 이유가 없다 |
| `goal` | `side`, `score` | 골. 공은 서버가 중앙으로 되돌린다 |
| `park` | `park` (`{seesaw, carousel, carouselSpeed}`) | 놀이기구 상태(시소 기울기·뺑뺑이 각도). **움직일 때만** 보낸다 |
| `system` | `text`, `kind`, `token` | 서버가 모두에게 보내는 알림(입장·퇴장). 클라이언트가 각자 문구를 만들면 사람마다 다른 문장을 보게 되고, 놓친 이벤트는 아무에게도 안 보인다. 본인의 입장 알림은 본인에게 보내지 않는다 |
| `error` | `code`, `message` | 거부 사유(레이트 리밋·이름 길이 등) |

## 3. 서버가 강제하는 것 (검증 규칙)

| 규칙 | 값 | 이유 |
|---|---|---|
| 활동별 이동 속도 상한 | `data/activities.json`의 `speed` × 1.6 | 자전거(7.6)는 걷기(4.2)보다 빨라야 하고, 그 값을 서버가 모르면 자전거를 탄 사람의 위치를 계속 되돌린다. 반대로 상한을 항상 자전거에 맞추면 걸어가면서 자전거 속도로 순간이동할 수 있다 |
| 공 차기: 활동·사거리 | 축구 중 + 1.5유닛 이내 | 그러지 않으면 맵 반대편에서 공을 골대에 넣을 수 있다 |
| 운동장 전용 운동은 위치 검사 | 시작할 때 **그리고 이동할 때마다** | 시작만 검사하면 운동장 안에서 켜고 나가 섬 전역을 자전거 상한(12.16)으로 돌아다닐 수 있다 — 검사가 왕복 한 번을 더한 것에 그친다. 벗어나면 서버가 해제하고 모두에게 알린다. 여유 1.5유닛을 두는 이유는 서버 좌표가 최대 한 틱 뒤처지기 때문이다 |
| 운동 전환 간격 | 250ms | 전원 브로드캐스트 + 저장 표시를 유발하고, 받는 쪽은 처음 보는 (운동, 기술) 조합마다 스프라이트 프레임을 새로 만든다. **거부하면 권위 상태를 요청자에게 돌려보낸다** — 클라이언트는 반응성을 위해 먼저 로컬에 적용하므로, 아무 응답도 없으면 화면과 서버가 갈리고 속도 상한까지 어긋나 이동이 고무줄이 된다 |
| 놀이기구 좌석 배정 | 서버가 빈 자리를 정한다 | 클라이언트가 정하면 두 사람이 같은 좌석에 겹쳐 앉는다. 찬 자리를 요청하면 빈 자리로 옮기고, 없으면 `seat_taken` |
| 앉은 사람의 위치 | 좌석에서 0.6유닛 이내(`RIDE_LEASH`) | 좌석 배정으로 겹침만 막고 좌표는 클라이언트 주장을 받으면, 놀이기구에 앉은 채 섬을 돌아다닐 수 있다 |
| 놀이기구 밀기 | 타고 있는 사람만 + 간격 제한 | 지나가면서 남의 기구를 흔들 수는 없다 |
| `trick` 형식(자유 형식 활동) | `자리` 또는 `자리:진폭`, 둘 다 유효 범위의 정수 | 그대로 방송되고 받는 쪽은 처음 보는 (운동, 기술) 조합마다 스프라이트를 새로 만든다 — 임의 문자열을 허용하면 남의 클라이언트에 프레임 스파이크를 먹일 수 있다 |
| 축구 값 유효범위 | friction 0<f<1, 속도·사거리 > 0 | friction이 음수면 `pow(음수, 0.1)`이 NaN이 되어 공 좌표가 NaN으로 퍼지고, 공이 사라진 채 서버 재시작까지 복구되지 않는다 |
| 재접속 시 운동 상태 초기화 | join에서 (끊겼던 경우만) | 새 클라이언트는 아무 운동도 안 하는 상태로 시작한다. 서버가 옛 상태를 들고 있으면 남들 화면에 계속 자전거가 보이고 이동 상한도 열려 있다(rename도 join을 거치므로 접속이 유지된 경우는 건드리지 않는다) |
| 공 물리·골 판정 | 서버 tick(10Hz) | 클라이언트가 각자 굴리면 기기마다 공 위치가 달라 "내 화면에서는 골"이 된다 |
| 월드 경계 | `data/world.json`의 size로 클램프 | 맵 밖으로 나가는 좌표 차단 |
| 이동 속도 상한 | 클라이언트 이동속도의 1.6배 | 순간이동/속도핵 완화(정확한 시뮬레이션은 아님) |
| 이름 | 1~12자, 앞뒤 공백 제거, 제어문자 금지 | 렌더 깨짐·오버플로 방지 |
| 채팅 | 최대 200자, 초당 2건 | 도배 방지 |
| 이모티콘 | 화이트리스트(`data/emotes.json`)에 있는 id만 | 임의 문자열 표시 방지 |
| 채집 | 초당 4건, `data/items.json`에 있는 아이템만 | 연타 도배·임의 아이템 생성 방지 |
| 판매 | 초당 2.5건, 금액은 서버가 계산(유효범위 클램프) | 벨 조작 방지 |
| 스폰 위치 | 접속 순서에 따라 링(반지름 1.3, 8자리) 위로 분산 | 새 캐릭터가 스폰 지점에 모두 겹치는 것 방지. 무작위가 아니라 결정적이어야 테스트가 재현된다 |
| 월드 아이템 총량 | 최대 300개 | 무한 드랍으로 서버 메모리·클라이언트 렌더 폭발 방지 |
| 아이템 소유권 | 줍기는 **선착 1명**만 성공, 실패는 조용히 무시하지 않고 `error` 반환 | 중복 획득 방지 |

**신뢰 경계 명시**: 클라이언트가 보낸 `x/z`는 위 상한 안에서는 그대로 수용된다. 바위 통과와 캐릭터 겹침도 서버가 검증하지 않는다(각 클라이언트가 자기 자신을 밀어내는 방식). 즉 벽 통과·존 진입 조건 우회는 막지 못한다. 미니게임처럼 결과가 걸린 상호작용을 붙일 때는 그 판정만 서버로 옮겨야 한다(로드맵 P5에 명시).

## 4. 영속

- **벨과 가방은 서버가 소유한다.** 예전에는 판매가 클라이언트에만 반영돼, 재접속 시 `welcome`이 서버 가방으로 덮어쓰면서 판 물건이 되살아나고 벨은 그대로 남는 무한 획득 경로가 있었다(2026-09-04 발견). 벨을 서버 레코드에 두면 기기 간 이전도 자연히 해결된다.
- 서버는 캐릭터 레코드와 월드 아이템을 `server/data/world.json`에 저장한다. 저장은 **변경 후 2초 디바운스 + 30초 주기**이며, 쓰기는 임시 파일에 쓴 뒤 rename 하는 방식(중간에 죽어도 파일이 반쯤 쓰인 상태로 남지 않게).
- 서버가 끊긴 동안 채집한 것은 클라이언트가 버퍼에 쌓아두고 **재연결 시 `gather`로 흘려보낸다** — 안 그러면 서버의 `welcome`이 로컬 가방을 덮어써 오프라인 채집이 사라진다(`world.gd::_pending_gathers`).
- 클라이언트 세이브(`user://save.json`)는 **토큰과 슬롯 목록**의 출처이고, 위치·인벤토리는 서버가 우선이다. 오프라인(서버 연결 실패)에서도 혼자 플레이할 수 있게 클라이언트도 마지막 상태를 들고 있지만, 서버에 붙는 순간 서버 값으로 덮는다 — 두 출처가 갈릴 때 어느 쪽이 이기는지 정해두지 않으면 진행도가 사라지는 사고가 난다.
