# 아이들이 좋아할 추가 콘텐츠 후보 (2026-09-15)

대상: "아이들이 좋아할 만한 추가 콘텐츠"를 넓게 뽑고 우선순위를 정한다.

> 이 문서는 `docs/agents/roles.md` §1 가상 페르소나(창의/기획)의 산출물이다.
> 밸런스 수치·프로토콜 변경의 **정합성 판정은 구현 시점에 실제 CLI 교차검증**으로
> 따로 받는다.

## 0. 전제 — 이 게임의 플레이어는 누구인가

서버 상태 파일의 캐릭터는 **형제자매 + 어른이 한 섬에 같이 접속**하는 구성이다.
그래서 일반적인 "아이들용 콘텐츠"와 다른 제약이 둘 붙는다.

- **나이가 섞인다.** 글을 아직 못 읽는 아이가 섞이면 텍스트로 설명하는 기능은
  그 아이에게 없는 기능이다 — 아이콘·색·움직임·소리로 알 수 있어야 한다.
- **형제자매는 경쟁만 시키면 싸운다.** 지금 있는 승부 콘텐츠는 달리기 경주뿐이고,
  **협동으로 이기는 것**이 하나도 없다. 같이 하면 더 좋은 쪽을 의도적으로 넣는다.

## 1. 지금 비어 있는 곳 (코드로 확인한 사실)

| 구멍 | 확인 | 아이 관점에서의 의미 |
|---|---|---|
| **벨을 쓸 곳이 없다** | 서버에 구매 경로가 **한 줄도 없다**(`sell`만 있고 `buy` 없음) | 모으는 이유가 없다. "사는 재미"가 통째로 빠져 있다 |
| **소리가 없다** | 게임에 사운드 코드가 없고, http라 `AudioWorklet` 자체가 차단됨(`web/shell.html`) | 어린아이에게 가장 즉각적인 피드백 수단이 없다 |
| **섬은 넓은데 갈 이유가 몰려 있다** | 섬 76×42.75, 할 것은 운동장·놀이터·물가에 집중 | 넓은 곳이 "지나가는 길"이라 탐험의 보상이 없다 |
| 도감 16종 | `data/items.json` | 다 모으면 끝이다. 자랑할 축이 "개수" 하나뿐 |

## 2. 페르소나별 관점

### 🎮 GameDesigner — 루프에 기여하지 않으면 자른다
지금 루프는 **채집 → 판매 → (끝)** 이다. 부탁·도감이 목적을 조금 주지만 벨은 여전히
숫자로만 쌓인다. **소비처를 만드는 것이 신규 콘텐츠보다 먼저**다 — 소비처가 생기면
기존 채집·낚시·부탁이 전부 의미가 커진다(같은 코드로 재미가 오른다).

### 🗺️ LevelDesigner — 자극 밀도와 "갈 이유"
섬을 1.5배로 키운 뒤 빈 곳이 늘었다. **매일 자리가 바뀌는 목표**를 섬 구석에 두면
넓이가 비용이 아니라 자산이 된다. 새 지형을 만들 필요가 없다는 점이 중요하다.

### ⚖️ EconomyBalancer — 벌기만 하고 쓰지 않는 경제
부탁 보상이 판매가 ×1.8이라 **획득 곡선만 있고 소비 곡선이 없다**. 지금은 인플레가
문제가 아니라 **아무 의미가 없는 상태**다. 소비처를 넣을 때 가격대를 셋(하루치 /
이틀치 / 일주일치)으로 나눠 "오늘 살 것"과 "모아서 살 것"을 구분한다.

### 🎨 UIUXDesigner — 글을 못 읽는 플레이어
설명이 필요한 기능은 **아이콘과 즉시 피드백**으로 대체할 수 있는지 먼저 본다.
보물찾기의 "따뜻해/차가워"를 글자 대신 **색과 소리 간격**으로 주면 글을 몰라도 된다.

### 🖌️ ArtDirector — 에셋 0 원칙은 그대로
새 콘텐츠도 전부 절차적으로 만들 수 있어야 한다. 상점 물건은 **팔레트 조합**,
날씨는 **파티클과 색 보정**, 보물 상자는 **프리미티브**로 충분하다.

### ⚙️ TechAnalyst — 스냅샷 예산
펫처럼 **인원수만큼 늘어나는 엔티티**는 10Hz 스냅샷을 키운다(N명 × 펫). 반면 날씨·
보물 위치는 **하루에 한 번 씨앗만 방송**하면 되므로 사실상 공짜다. 비용 차이가 열 배
이상이라 우선순위에 반영한다.

### 🧪 QAEngineer — "됐다"의 판정 기준
승부가 걸린 것(술래잡기)은 경주와 같은 형태로 **서버가 판정**해야 테스트가 된다.
닿음 판정은 사거리 판정과 같은 부류이므로 `lagPadOf`(지연 여유)를 그대로 쓴다.

### 👑 PMOrchestrator — 스코프 경계
아래 목록에서 **한 번에 하나씩** 간다. "집 꾸미기"처럼 큰 것은 이번 라운드에서
제외하고, 같은 재미를 **작게** 주는 대체안을 먼저 넣는다.

## 4. 우선순위 추천

**1순위: A1 상점** — 유일하게 **기존 콘텐츠 전부의 가치를 올리는** 후보다. 채집·낚시·
부탁이 전부 "살 것을 위한 것"이 된다. 꾸미기 화이트리스트가 이미 서버에 있어서
"산 것만 열어 준다"로 확장하는 형태라 구조도 맞는다.

**2순위: B2 보물찾기** — 넓어진 섬에 갈 이유를 만들고, 글을 못 읽는 아이도 색과 소리
간격으로 참여한다. 여럿이 나눠 찾으면 빨라지니 **협동이 이득**인 첫 콘텐츠다.

**3순위: C1+C2 크기·칭호** — 둘 다 작고, "자랑"이라는 축을 새로 만든다. 남의 화면에
보이는 것(칭호)이 형제자매에게는 보상이다.

**4순위: B1 술래잡기** — 재미는 가장 확실하지만 서버 판정이 필요해 규모가 있다.
경주가 만든 상태 기계를 재사용할 수 있게 된 지금이 적기다.

**5순위: F1 소리** — 아이 반응은 가장 크지만 **https 전환**이라는 별개 작업이 앞에
있다. 폰 접속 방식(자체 서명 인증서 경고 / 도메인+정식 인증서)을 먼저 정해야 한다.

### 이번 라운드에서 제외

- **A3 집/가구**, **B4 숨바꼭질**, **E1 펫** — 전부 대규모다. 특히 펫은 10Hz 스냅샷이
  인원수만큼 커진다. 같은 재미를 A2(장난감)·C2(칭호)가 **작게** 대신한다.
- **E2 사진 모드** — 폰 브라우저의 저장 제약을 먼저 확인해야 한다(확인 전에는 규모를
  말할 수 없다).

## 5. 다음 단계

우선순위 중 하나를 고르면 그 항목만 **설계 회의를 따로** 연다(F1~F5 때와 같은 형식) —
데이터 스키마, 서버 판정 범위, 테스트 판정 기준을 정한 뒤 구현한다.
