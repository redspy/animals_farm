## 1. 현재 상태 점검 (TechAnalyst)

**TechAnalyst**: 지금 코드는 폰을 전혀 고려하지 않았습니다. 세 가지가 구조적으로 걸립니다.

1. **HUD가 절대좌표**입니다. `world.gd::_build_hud`가 `Vector2(16, 12)`, `(16, 250)`, `(760, 12)`, `(16, 500)` 같은 픽셀 좌표를 직접 씁니다. 프로젝트 stretch가 `canvas_items` + `expand`라서 기준 해상도(960×540)보다 좁거나 세로로 길면 **화면 밖으로 나가거나 겹칩니다**. 특히 `(760, 12)`의 접속 상태 라벨은 세로 모드에서 잘립니다.
2. **입력이 키보드 전용**입니다. `player.gd`는 `Input.get_axis("ui_left", ...)`만 읽고, `world.gd::_unhandled_input`은 `KEY_S/T/Q/1~6`을 직접 봅니다. 터치에서는 아무것도 동작하지 않습니다.
3. **동시 입력**이 필요합니다. 이동하면서 채집/이모티콘을 누르는 상황이 흔하므로 마우스 에뮬레이션(`InputEventMouseButton`)만으로는 부족하고 `InputEventScreenTouch`/`InputEventScreenDrag`의 **터치 index를 추적**해야 합니다.

**PMOrchestrator**: 그럼 이번 작업의 범위는 (a) 레이아웃을 앵커 기반으로 전환, (b) 터치 조작 UI 신설, (c) 폰에서의 카메라·성능 조정. 채팅 입력의 한글 IME는 검증 항목으로 분리합니다.

## 2. 이동 조작: 무엇으로 할까

**GameDesigner**: 세 후보가 있습니다 — 가상 조이스틱, D-패드, 탭-투-무브.

**LevelDesigner**: 탭-투-무브는 이 게임에 안 맞습니다. 채집 상호작용 거리가 1.6 월드 유닛이고 채집물이 24개가 흩어져 있어서, "저 나무 옆에 정확히 서기"를 반복해야 합니다. 탭으로는 미세 조정이 어렵고, 나중에 다른 캐릭터와 나란히 서서 대화하는 상황(모임 존)에서 특히 답답해집니다.

**UIUXDesigner**: D-패드는 8방향이 끊겨서 산책하는 느낌을 깎습니다. 이 게임은 속도 4.2로 느긋하게 걷는 게임이고, 아날로그로 방향을 바꾸는 감각이 어울립니다.

**결정 ①**: **플로팅 가상 조이스틱**(왼쪽 하단 영역). 화면 왼쪽 아래 영역 **어디를 눌러도 그 지점이 조이스틱 중심**이 되는 방식으로 한다 — 고정 조이스틱은 엄지 위치 편차 때문에 매번 위치를 확인해야 해서 시선을 아래로 끌어내린다.
**보완**: 방향키 입력도 계속 살린다(폰에 블루투스 키보드를 붙이거나 데스크톱에서 터치 UI가 뜨는 경우 대비). 두 입력은 합산하지 않고 **더 큰 쪽을 쓴다**.

## 3. 액션 버튼 배치

**UIUXDesigner**: 엄지 도달 범위를 기준으로 하면 오른손 엄지는 화면 우하단 반경 안이 편합니다. 주 액션은 가장 크고 가장 아래에, 부수 액션은 그 위로 올립니다. 최소 터치 타깃은 **44dp**가 하한이고 주 액션은 **72dp** 정도가 안전합니다.

**EconomyBalancer**: 판매(`S`)는 **버튼으로 내놓지 마세요**. 되돌릴 수 없는 동작이고, 지금은 가방 전체를 파는 구조라 오조작 한 번에 수집품이 사라집니다. PC에서도 위험하지만 폰에서는 오조작 확률이 훨씬 큽니다.

**GameDesigner**: 동의합니다. 판매는 HUD의 가방 줄을 탭하면 **확인 시트**를 띄우고 거기서 확정하는 걸로 옮깁시다.

**결정 ②**: 우하단 배치.
| 버튼 | 크기 | 동작 |
|---|---|---|
| 채집/줍기 (주 액션) | 72 | 기존 `Space` — 근처 물건이 있으면 줍고 없으면 채집 |
| 채팅 | 56 | 입력창 열기 + 가상 키보드 |
| 이모티콘 | 56 | 하단 시트 열기 |
| 버리기 | 48 | 가방에서 1개 놓기 |
| 판매 | — | 버튼 없음. HUD 가방 줄 탭 → 확인 시트 |

## 4. 이모티콘 선택 방식

**UIUXDesigner**: 롱프레스 휠은 모바일 웹에서 위험합니다. 브라우저가 롱프레스를 텍스트 선택/컨텍스트 메뉴로 가로채는 경우가 있어 조작이 씹힙니다. 버튼 6개를 항상 띄우면 화면을 너무 먹습니다.

**결정 ③**: 이모티콘 버튼 탭 → **하단 시트에 6칸 그리드**(개수는 `data/emotes.json`이 정한다). 하나 고르면 즉시 전송하고 시트를 닫는다. 시트 밖을 탭하면 취소.

## 5. 채팅 입력과 한글 IME

**TechAnalyst**: 폰에서 텍스트를 입력하려면 가상 키보드가 떠야 합니다. 두 가지 길이 있습니다.
- (A) Godot의 웹 가상 키보드: export 옵션 `html/experimental_virtual_keyboard`를 켜고 `DisplayServer.virtual_keyboard_show()`를 부른다. 이름에 "experimental"이 붙어 있는 만큼 신뢰도가 확실하지 않고, **한글 IME 조합**(초성·중성·종성이 조합되는 과정)이 캔버스 입력에서 깨질 가능성이 있습니다.
- (B) `JavaScriptBridge`로 캔버스 위에 실제 DOM `<input>`을 얹는다. 브라우저 네이티브 입력이라 IME는 확실하지만, 캔버스와 DOM을 겹치는 레이아웃·포커스 관리 코드가 늘어납니다.

**QAEngineer**: 여기서 중요한 건 **우리가 아직 한글 입력을 한 번도 실기에서 확인하지 않았다**는 점입니다. 자동 테스트는 합성 키 이벤트라 한글이 아예 들어가지 않아 ASCII로만 검증했습니다. 그러니 "(A)가 된다/안 된다"를 지금 단정할 수 없습니다.

**결정 ④**: **(A)를 먼저 넣고, 실기 확인 후 필요하면 (B)로 교체**한다. 교체 비용을 줄이기 위해 채팅 입력을 `world.gd`에서 직접 다루지 말고 **입력 경로를 한 군데(`ChatInput`)로 모아** 구현한다. (A)/(B) 어느 쪽이든 바뀌는 파일이 하나여야 한다.
**검증 항목(사람)**: 폰에서 ① 키보드가 뜨는가 ② 한글이 조합되어 들어가는가 ③ 전송 후 키보드가 닫히는가.

## 6. 세로 모드와 카메라

**ArtDirector**: 직교 카메라 `size`는 **세로 기준**입니다. 세로 모드(예: 390×844)에서는 세로 시야가 그대로고 가로가 확 좁아져서, 화면에 보이는 월드가 위아래로 길쭉해집니다. 산책 게임에서 좌우가 좁으면 답답합니다.

**결정 ⑤**: 화면 비율에 따라 카메라 `size`를 보정한다. 기준 비율(16:9)보다 세로로 길면 `size`를 줄여 **가로 시야를 확보**하고, 캐릭터가 지나치게 작아지지 않도록 하한을 둔다. 값은 구현에서 상수로 노출하고 실기에서 조정한다.

## 7. 폰 성능

**TechAnalyst**: 지금 방향광 그림자가 켜져 있습니다. GL Compatibility(WebGL2) + nothreads 환경의 저사양 폰에서는 그림자 맵이 가장 먼저 문제가 됩니다.

**ArtDirector**: 다만 그림자를 그냥 끄면 2D 빌보드 캐릭터가 지면에서 떠 보입니다. 캐릭터 발밑 그림자는 별도 타원 데칼이라 그림자 맵과 무관하니, **방향광 그림자만 끄면** 캐릭터 접지감은 유지됩니다.

**결정 ⑥**: 터치 환경(모바일)로 판단되면 **방향광 그림자를 끈다**. 발밑 타원 데칼은 유지. 다른 최적화는 실기에서 프레임을 보고 결정한다.

## 9. Gemini(`agy`) 자문 결과 반영

`agy`에 현재 화면 캡쳐(`build/screenshots/chat-ui/`)와 설계 문서를 주고 같은 7개 질문을 던졌다. 회신 내용과 이 회의의 결론을 대조한 결과는 아래 §10 "확정 사항"에 병합했고, 갈린 지점만 여기 남긴다.

`agy`는 7개 항목 중 5개에서 패널과 같은 결론을 냈다(절대좌표 UI 잘림, 동적 가상 조이스틱, 판매 격리, 세로 모드 카메라 보정, 방향광 그림자 우선 차단). **갈린 두 지점**과 처리:

### (가) 이모티콘 선택 — 롱프레스 휠 vs 하단 시트

- **agy**: 롱프레스 방사형 휠 추천. "6개는 방사형에 완벽한 개수이고, 평소 화면 공간을 전혀 쓰지 않으며 대화 흐름을 끊지 않는다."
- **UIUXDesigner(패널)**: 모바일 웹에서 롱프레스는 브라우저의 텍스트 선택·컨텍스트 메뉴(iOS Safari의 callout 포함)에 가로채일 수 있다. 그걸 막으려면 캔버스 셸의 CSS/이벤트 처리에 의존해야 하는데, 우리가 통제하지 않는 부분이다.
- **결정: 하단 시트로 먼저 구현한다.** 시트도 필요할 때만 열리므로 "평소 공간을 쓴다"는 단점은 없다. 휠은 롱프레스가 실기에서 안전하다고 확인된 뒤 대안으로 검토한다 — **확실히 동작하는 쪽을 먼저 넣고, 더 빠른 쪽은 검증 후에** 올린다.

### (나) 채팅 입력 — Godot 가상 키보드 vs DOM 오버레이

- **agy**: DOM `<input>` 오버레이가 "압도적으로 안전". Godot Web의 `experimental_virtual_keyboard`는 모바일 브라우저 파편화로 **한글 IME 조합이 풀리거나 글자가 두 번 입력되는** 문제가 잦다고 지적.
- **TechAnalyst(패널)**: 원래는 싼 쪽(A)을 먼저 넣고 실기에서 깨지면 (B)로 가자는 순서였다. 그런데 이 게임은 한국어 채팅이 기능의 핵심이고, (A)가 깨지면 **사용자가 글자를 잃는** 실패 모드다. 재작업 비용도 (B)를 나중에 넣는 것과 처음부터 넣는 것이 크게 다르지 않다.
- **결정: agy 의견을 채택해 처음부터 DOM 오버레이로 간다.** 단 데스크톱/에디터에는 DOM이 없으므로 `chat_input.gd` 한 파일 안에서 **웹이면 DOM `<input>`, 아니면 기존 `LineEdit`** 으로 갈라진다. 어느 쪽이든 바깥 코드는 같은 API(`open()`/`submitted` 시그널)만 본다.
- ⚠️ 이 결정의 근거는 `agy`가 말한 Godot 웹 IME 실패 사례이며 **우리가 직접 확인한 것은 아니다**. DOM 쪽은 브라우저 네이티브 입력이라 IME가 깨질 이유가 없다는 점이 채택의 실질적 근거다.

### 참고: agy가 추가로 지적한 것

- 판매는 "가방 UI를 열고 그 안에서 두 번 확인"까지 격리하라는 의견. 패널은 **가방 줄 탭 → 확인 시트 1회**로 정했다. 전체 판매는 경고 문구가 명확하면 1회 확인으로 충분하다고 보고, 가방 전용 화면은 인벤토리 UI(P6)에서 함께 만든다.
- 채팅/이모티콘 버튼을 좌측 중단이나 상단에 두라는 의견. 패널은 우하단 스택을 유지한다 — 왼쪽 하단은 조이스틱 영역이고, 상단은 엄지에서 가장 먼 자리다.

**터치 UI를 언제 띄우는가**: `DisplayServer.is_touchscreen_available()`이 참일 때 띄운다. 노트북 터치스크린에서도 뜨지만 그게 오답은 아니다 — 반대로 폰에서 안 뜨는 쪽이 치명적이므로 "의심스러우면 띄운다"로 간다. 강제 토글은 나중에 설정 화면(P6)에서.
