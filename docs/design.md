# Animals Farm — 게임 설계 문서

## 0. 한 줄 정의

닌텐도 스위치 **『동물의 숲』을 모티브로 한 브라우저 게임**. Godot 4(GDScript) + 웹(HTML5) export로 만들고, 사용자 소유 서버에서 정적 서빙한다.

- 확정: 엔진/언어(Godot 4, GDScript), 배포 형태(웹), 모티브(동물의 숲), 배포 파이프라인(`docs/deploy.md`)
- 진행 중: 코어 루프의 최소 1사이클 프로토타입(`scripts/main.gd` — 채집 → 가방 → 판매 → 자동 저장)
- 미확정: 이웃 동물 AI/대화, 집·마을 꾸미기, 도감, 멀티플레이 여부, 아트 톤&매너

원작을 그대로 복제하는 것이 목표가 아니다. 원작의 IP 자산(캐릭터·이름·에셋·음악)은 사용하지 않고, **차용하는 것은 게임 구조(느린 실시간 루프, 수집, 꾸미기, 이웃과의 관계)뿐**이다.

## 1. 코어 루프

원작의 핵심은 "짧게 접속해도 매일 조금씩 달라져 있는 마을"이다. 그래서 루프의 단위는 세션이 아니라 **하루**다.

1. **접속** — 현실 시간이 곧 게임 시간(`scripts/game_clock.gd`). 현재는 계절·시각이 **HUD 표시에만** 쓰인다 — 계절/시각에 따른 스폰 변화는 *미구현*.
2. **일일 갱신** — 마지막 접속 이후 하루가 지났으면 채집물이 전부 되살아난다(`GameClock.days_since`). 일일 이벤트 시스템은 *미구현*.
3. **채집** — 나무·조개·잡초 등을 모은다(`scripts/gatherable.gd`, 배치는 `data/gatherables.json`).
4. **환금** — 모은 것을 팔아 벨(재화)을 얻는다(가격은 `data/items.json`이 유일한 출처).
5. **투자** — 벨을 집·마을 꾸미기와 도구 확장에 쓴다 *(미구현 — 다음 단계)*.
6. **관계** — 이웃 동물의 의뢰를 받고 친밀도를 올린다 *(미구현 — 다음 단계)*.

**설계 원칙**: 접속 1회에 할 일을 다 못 끝내게 만들지 않는다. 하루치 콘텐츠는 5~10분에 소진되어야 하고, 남은 것은 "내일"로 넘긴다. 이 원칙에 기여하지 않는 기능은 제안 단계에서 잘라낸다(`docs/agents/roles.md` GameDesigner).

### 2.1 2.5D 화면 구성

"2D와 3D가 섞인" 룩을 다음 세 층으로 만든다.

| 층 | 무엇 | 구현 |
|---|---|---|
| 3D 월드 | 섬(두께 있는 박스) · 모래 테두리 · 바다 · 나무(원기둥+구) · 조개 · 잡초 | `main.gd::_build_environment`, `gatherable.gd` — 전부 Godot 프리미티브 메시. 방향광 그림자가 있어 입체로 읽힌다 |
| 2D 캐릭터 | 플레이어 (32×40 픽셀 스프라이트, 4방향 × 걷기 6프레임 10FPS + idle) | `player_sprite.gd` — `AnimatedSprite3D` 빌보드. 프레임은 **런타임에 픽셀로 생성**(외부 아트 에셋 0개), 좌측은 우측 프레임을 반전해 재사용 |
| 2D UI | 시계·벨·가방·조작 안내·토스트 | `main.gd::_build_hud`가 `CanvasLayer` + 빈 `Label`을 만들고, 문구 조립은 `main.gd::_refresh_hud`가 한다(고칠 때 두 함수를 함께 볼 것) |

카메라는 **직교 투영**(`PROJECTION_ORTHOGONAL`, size 9.5)에 pitch -38°, yaw 0°이고 플레이어를 부드럽게 따라간다. yaw를 0으로 고정한 이유는 화면 위쪽이 월드 -Z와 일치해 입력 매핑이 단순해지기 때문이다 — 카메라를 회전시키면 `player.gd`의 입력→월드 변환도 같이 고쳐야 한다.

빌보드 캐릭터에서 실측으로 걸린 함정 세 가지(2026-09-04, 브라우저):
- 완전 빌보드(`BILLBOARD_ENABLED`)는 카메라 피치까지 따라가 캐릭터가 뒤로 누운 것처럼 보인다 → `BILLBOARD_FIXED_Y`
- 노드 원점이 스프라이트 중앙이면 배치가 어긋난다 → `offset`으로 원점을 발바닥에 맞춤
- 빌보드가 방향광 그림자를 드리우면 공중에 뜬 얼룩처럼 보인다 → 스프라이트 그림자는 끄고, 발밑에 타원 데칼을 따로 깐다(`player.gd::_add_ground_shadow`)

`player_sprite.gd`는 **Gemini CLI(`agy`)가 구현**했다 — 걷기 사이클처럼 결과를 눈으로 판정하는 작업을 다른 모델에 맡기고, 이 세션은 계약(애니메이션 이름 8개, `set_move_dir`/`facing` API, 웹 제약)과 검증(헤드리스 + 브라우저 스모크)을 담당했다(`docs/agents/roles.md` §3).

## 3. 밸런스·경제 데이터 규칙

같은 원칙이 색에도 적용된다: 수치는 `data/items.json`·`data/gatherables.json`, 색은 `data/palette.json`이 단일 출처이며 코드는 읽어 쓰기만 한다(`Balance`, `Palette`).

- 수치는 코드에 흩뿌리지 않고 `data/*.json`에만 둔다. 유효범위도 **주석이 아니라 구조화된 필드**로 데이터에 둔다 — `items.json`은 항목별 `price_range`, `gatherables.json`은 최상위 `limits`(예: `respawn_sec: [10, 86400]`)가 단일 출처다. 코드에 범위를 하드코딩하면 이 규칙이 깨진다(2026-09-03 Codex 감사 지적으로 `gatherable.gd`의 하드코딩 범위를 제거).
- 코드는 데이터를 읽을 때 유효범위로 **항상 클램프하고 항상 경고를 남긴다**. 이 규칙은 `scripts/balance.gd`(`Balance.clamp_value`)가 단독 소유하며 가격·리스폰 양쪽이 같은 코드를 쓴다. 범위가 없거나 `[lo, hi]` 형식이 아니거나 `lo > hi`면 폴백 범위를 적용하고 경고한다 — 폴백은 **출처가 아니라 데이터가 깨졌을 때의 마지막 안전장치**다.
- `data/items.json`에 없는 아이템은 0벨로 조용히 처리하지 않는다(판매 시 가방에서 사라져 플레이어 손실이 된다) — 판매 대상에서 제외하고 가방에 남기며 경고한다.
- 밸런스 변경은 `data/` 파일만 바뀌어 코드 확장자가 없는 커밋이 되기 쉬운데, pre-commit 게이트는 `.json`도 리뷰 대상에 포함한다(`scripts/review.js`의 diff 필터).

## 4. 세이브 데이터 스키마

```jsonc
{ "version": 1, "bells": 0, "inventory": { "wood": 3 },
  "first_played_unix": 0, "last_played_unix": 0 }
```

- `version` 필드는 필수. 마이그레이션은 `SaveManager.migrate()` 한 곳에서만 하고, **각 단계마다 손실 여부를 주석으로 명시**한다.
- 미래 버전 세이브(다운그레이드)는 마이그레이션하지 않고 `_read_only`로 잠근다 — 신버전에서 만든 데이터를 구버전이 덮어써 잃는 사고를 막는다.
- 손상된 세이브는 조용히 덮어쓰지 않고 `save.json.corrupt`로 백업한 뒤 새로 시작한다.
- v0(버전 필드 없는 세이브) → v1 마이그레이션은 누락 필드를 전부 채운다. `first_played_unix`는 복구 불가능한 정보라 현재 시각으로 채우고 그 사실을 경고로 남긴다.
- **회귀 테스트**: `tests/test_save_migration.gd`(v0→v1 필드/값 보존, 미래 버전 읽기 전용, 손상 세이브 폴백). `./scripts/verify-project.sh`가 실행한다 — 표준 Godot 빌드가 필요하다.
- **스키마 변경 절차**(`docs/agents/roles.md` §4): TechAnalyst+QAEngineer 페르소나 검토 → 3종 CLI 교차검증(`npm run panel`) → 구버전 세이브 로드 회귀 테스트. 진행도 손실은 되돌릴 수 없다.

## 5. 비주얼 가이드라인

전체 가이드라인은 아직 미확정이지만, **캐릭터 층은 코드에 확정됐다**(2026-09-04). "그레이박스(도형만)" 서술은 더 이상 정확하지 않으므로 확정된 것과 아닌 것을 나눠 적는다.

|---|---|---|
| 폰트 | Noto Sans KR(OFL) 임베드 — 웹은 시스템 폰트 폴백이 없어 한글이 두부(□)가 된다 | `project.godot`의 `gui/theme/custom_font` |

색 하나를 바꾸려면 `data/palette.json`만 고치면 된다. `tests/test_palette.gd`가 **`scripts/*.gd`를 스캔해 실제 호출된 `Palette.color(group, key)`를 추출**해 데이터와 대조하므로(키 목록을 테스트에 다시 적지 않는다), 코드가 없는 키를 참조하면 커밋 전에 걸린다. 팔레트에 없는 키를 요청하면 **마젠타(#ff00ff)로 그려지고 경고가 남는다** — 화면에 마젠타가 보이면 키 누락이라는 뜻이므로, 조용히 검은색으로 대체해 눈치채지 못하는 상황을 피한다.

### 도트 캐릭터 규칙 (사람·동물 공통, 2026-09-07)

캐릭터를 "얼굴 없는 색 덩어리"에서 벗어나게 하면서 **기존 좌표를 깨지 않기 위한** 규칙이다. 눈으로 보고 정한 것이므로 그림을 고칠 때도 같은 방법으로 확인한다 — **`npm run sprites`** 가 확대 시트 세 장(`build/sprite-sheet.png` 프리셋별, `sprite-activities.png` 활동별, `sprite-npc.png` 동물별)을 만든다. 게임 화면에서 캐릭터는 40~60px로 보이므로 코드만 읽고는 "얼굴이 보이는지"를 알 수 없다 — 첫 구현이 머리카락으로 얼굴을 통째로 덮고 있었다는 것도 시트를 뽑아 보고서야 알았다.

1. **좌표계는 논리 32×40 그대로, 이미지만 2배.** 좌표를 바꾸면 운동 장비 오버레이 8종(줄넘기·축구·자전거·인라인·킥보드·낚시·앉기·손잡이)을 전부 다시 찍어야 하고, 그 그림들은 몸 좌표에 손으로 맞춘 것이다. 프리미티브가 논리 좌표에 `SCALE`을 곱하므로 **기존 그림은 그대로**이면서 원이 매끄러워지고, 논리 1픽셀보다 작은 디테일(눈 하이라이트·볼·입)을 넣을 수 있다.
2. **표정은 머리카락을 그린 뒤에.** 순서가 뒤면 앞머리가 눈을 덮는다 — 첫 구현이 그래서 **얼굴이 아예 보이지 않았다**(머리 크기의 원으로 머리를 통째로 덮고 있었다). 앞머리는 **눈 위까지만** 그리고 길이는 얼굴 옆·뒤로 흘린다.
3. **눈은 흰자 한 겹 + 큰 눈동자 + 하이라이트 한 점.** 검은 덩어리를 크게 찍으면 무섭고, 흰자를 두껍게 두면 눈동자가 묻힌다. 원을 두 겹으로 겹치면 반지름 2~3에서 다이아몬드로 보이므로 눈동자는 사각으로 채운다.
4. **볼 홍조와 작은 입**을 넣는다 — 귀여움의 대부분이 여기서 온다.
5. **실루엣 외곽선을 맨 마지막에 한 번** 두른다. 없으면 풀색 배경에 옷·피부가 녹아 붙는다. 장비 오버레이까지 다 그린 뒤에 돌리므로 자전거·낚싯대도 같이 테두리를 얻는다. 구현은 **알파를 버퍼에서 한 번 읽고** 테두리 픽셀만 칠한다 — 픽셀마다 `get_pixel`로 이웃을 조회하면 스프라이트 생성이 몇 분 걸린다(실측: 5분 초과).
6. **음영은 한 줄만.** 턱·몸 아래를 반지름 절반 원으로 덮으면 얼굴 아래가 통째로 회색이 되어 지저분하다. 머리 윗광도 좌우 대칭 띠로 넣으면 "이마에 두른 띠"처럼 보이므로 **좌상단 짧은 호** 한 줄로 둔다.
7. **모자는 옷색을 쓰지 않는다.** 초록 옷 + 초록 모자면 머리와 몸이 한 덩어리가 된다(전용 `cap`/`cap_dark` 색). 챙은 **눈보다 위**에 둔다.
8. **동물도 같은 규칙**을 따르고 외곽선·표정 색을 사람과 **공유한다**(두 벌을 두면 화면에서 결이 갈린다). 몸통은 머리와 겹치게 시작하고 윗모서리를 깎는다 — 사각형을 머리 아래에 붙이면 "공 위에 상자를 올린" 이음선이 보인다.
9. **팔레트 그룹 안에는 주석 키를 두지 않는다.** `tests/test_palette.gd`가 그룹의 모든 값을 색 문자열로 검사한다 — `npc._comment`를 넣었다가 팔레트 테스트가 5개 커밋 동안 조용히 실패하고 있었다(내 검증 grep이 실패 줄을 가려서 못 봤다).

10. **장비는 자기 위상으로 발 위치를 다시 계산하지 말고 그 프레임의 실제 다리 좌표에 붙인다.** 다리는 6위상 보행 테이블인데 장비가 `phase % 2`·`phase % 3`로 흔들면 주기가 달라 **서로 반대로 움직인다**(실측 최대 8px 어긋남) — 게다가 들린 다리 밑에 기본 신발이 남아 발이 네 개로 보였다. 그래서 `_apply_activity`가 다리 좌표를 받아 인라인 부츠를 발에 붙인다.
11. **다리를 직접 그리는 활동(자전거·킥보드)과 앉는 자세는 기본 다리를 지우고, 그 활동에서만 걷기 위상을 끈다.** 지우는데 위상을 켜 두면 들린 다리가 지우는 사각형을 벗어나 상의 밑단에 혹처럼 남는다. 반대로 인라인은 다리가 보이는 게 정상이므로 목록에 넣지 않는다. 뺑뺑이는 `locked: true`라 걷기 위상이 0으로 고정된다는 **전제**에 의존한다 — 그 전제가 깨지면 목록에 추가해야 한다. 다리가 정규 위치 밖(위·옆)으로 나가면 덮는 사각형을 벗어나 상의 밑단이 옆으로 튀어나온 혹처럼 보이고, 외곽선이 그 혹까지 두른다. 지우는 사각형을 키우는 방법은 쓸 수 없다 — 노출된 다리 쪽과 **반대편 팔이 같은 열**에 오므로 핸들을 잡은 팔이 잘린다.
12. **비우는 함수는 논리/세밀 좌표를 섞지 말 것.** `_clear_rect`(논리)가 세밀 좌표를 만들어 넘긴 뒤 그쪽에서 다시 논리 프리미티브를 부르면 SCALE이 두 번 곱해져 **한 픽셀도 지워지지 않는다** — 자전거·킥보드에 선 다리가 남고 앉은 자세도 다리가 겹쳤는데, 외곽선이 맨 마지막에 돌아 그 다리에까지 테두리를 둘러 더 도드라졌다.

비용과 캐시
- 프레임 한 벌(4방향 × 6프레임) 생성이 5ms → **38ms**로 늘었다.
- 그래서 프레임 묶음을 **외형이 같으면 공유한다**(`static` 캐시, 키 = 외형 요약 + 성별 + 활동 + 기술). 인스턴스별로 캐시하면 같은 프리셋 8명이 같은 그림을 8번 만들고, 운동 중인 사람이 여럿인 월드에 접속할 때 그만큼 정지한다(8명이면 약 600ms).
- 캐시는 **12개로 제한**하고 **히트할 때 순서를 뒤로 옮긴다(LRU)**. FIFO로 두면 가장 먼저 만든 로컬 플레이어의 기본 모습이 가장 먼저 버려지고, 활동을 끝내는 그 프레임에 24장을 동기로 다시 만든다(웹에서 눈에 띄는 끊김이다). 정확히는 상한이 아니라 "캐시가 붙잡는 양"이다 — 축출해도 그 프레임을 쓰는 스프라이트가 살아 있으면 해제되지 않는다. 엔트리당 24장 × 64×80×4 ≈ 491KB이고 활동 조합이 15종쯤 되므로, 상한이 없으면 한 캐릭터가 다 돌면 7.5MB·여러 명이면 웹 힙에 물린다.
- 성별을 키에 넣는 이유: 치마 유무가 갈리므로, 같은 색·머리라도 공유하면 남성 프리셋에 치마가 붙는다.
- 반대로 **그림에 영향이 없는 값은 키에서 뺀다.** 놀이기구의 `trick`은 좌석·진폭이라 그림이 완전히 같은데(앉은 자세는 읽지 않는다) 키에 넣으면 그네 진폭 버튼을 누를 때마다 픽셀이 동일한 엔트리가 새로 생기고, 그 쓰레기 키들이 LRU를 밀어내 정작 지키려던 기본 모습이 축출된다.
- 상한은 **16**이다. 12까지 줄여 봤더니 멀티플레이 워킹셋보다 작았다 — 외형별로 키가 갈리므로 8명이면 기본 모습만 9칸이고 넷이 운동 중이면 13칸인데, 축출된 엔트리는 사용 중이면 해제되지도 않아 메모리는 그대로인 채 히트율만 떨어졌다. 16은 그 워킹셋을 덮으면서 예산(약 7.9MB) 안에 든다.
- **캐시 키에 넣을 값을 고를 때의 규칙**: 그리기에 영향을 주면 반드시 넣고(빠뜨리면 다른 외형이 프레임을 공유한다), 영향이 없으면 반드시 뺀다(넣으면 픽셀이 같은 엔트리가 쌓여 LRU를 밀어낸다). 두 실수 모두 캐시가 비워지지 않아 세션 내내 남는다.

### 미확정인 것

- 타일/오브젝트 스케일 규격, 애니메이션 원칙의 나머지(히트스톱 등), 아트 톤&매너.
- 팔레트는 "현재 색이 무엇인지"의 단일 출처일 뿐, "왜 그 색인지"(톤&매너)는 아직 문서화되지 않았다.

### `agy` 비주얼 패리티 리뷰의 현재 상태: **부분 활성**

- 캐릭터 스프라이트는 이미 `agy`가 구현하고 3라운드 피드백(빌보드 축 → 발바닥 원점/그림자 → 사이클 과장)으로 다듬었다(`docs/agents/roles.md` §3).
- 위 "미확정인 것"의 월드/UI 팔레트가 문서화되면 **전체 화면에 대한 필수 게이트로 승격**한다. 그때까지는 캐릭터 층에 한해 활용한다.

## 6. 조작

| 입력 | 동작 |
|---|---|
| **마우스 클릭 / 화면 탭** | **그 지점으로 이동. 나무·놓인 물건·다른 캐릭터를 누르면 다가가서 자동 처리** |
| 방향키 | 이동(누르는 순간 클릭 목표는 취소됨) |
| Space / Enter (`ui_accept`) | 주변에 놓인 물건이 있으면 줍고, 없으면 채집 |
| S | 가방 전부 판매 |
| T | 채팅 입력 열기 (Enter 전송, Esc 취소). **입력 중 맵을 클릭/탭하면 창이 닫히며 그 지점으로 이동한다** |
| Q | 가방에서 1개를 발밑에 놓기 |
| 1 ~ N | 감정 표현 이모지 (`data/emotes.json` 순서, 개수는 데이터가 정한다) |
| I 또는 S | 가방 화면(아이템별 판매·버리기) |

Godot 기본 입력맵(`ui_*`)과 직접 키코드만 사용해 커스텀 입력맵 없이 동작한다. 채팅 입력 중과 시트가 열린 동안에는 게임 조작을 받지 않는다 — 그러지 않으면 "s"를 치는 순간 물건이 팔리고, 시트 뒤에서 캐릭터가 움직인다.

### 터치 조작 (폰 브라우저)

`DisplayServer.is_touchscreen_available()`이 참이면 터치 UI가 뜬다. 설계 근거는 `docs/meetings/2026-09-04-1150-폰-터치-조작-설계.md`.

| 입력 | 동작 |
|---|---|
| 화면(월드) 탭 | 그 지점으로 이동. **대상을 탭하면 사거리까지 다가가 자동 채집/줍기**, 다른 캐릭터는 대화 거리까지 |
| 왼쪽 아래 영역을 누른 채 끌기 | **플로팅 가상 조이스틱** — 누른 지점이 중심이 되고, 기울인 만큼 천천히/빠르게 걷는다 |
| 우하단 큰 버튼 "채집" | 줍기/채집(키보드 Space와 동일) |
| "채팅" 버튼 | 입력창 열기 |
| "감정" 버튼 | 이모티콘 하단 시트(칸 수는 `data/emotes.json`이 정한다) |
| "버림" 버튼 | 가방에서 1개 놓기 |
| "가방" 버튼 | 가방 화면(아이템별 판매·버리기) |
| "스틱 ON/OFF" 버튼(좌하단) | 조이스틱 사용 여부 토글 — 끄면 이동은 탭만으로 하고, 조이스틱 영역도 평범한 월드 탭이 된다. 설정은 세이브에 남는다 |
| HUD 가방 줄 탭 | 판매 확인 시트 → 확정 시 전부 판매 |

**판매 버튼을 두지 않은 이유**: 되돌릴 수 없는 동작이라 오조작 한 번에 수집품이 사라진다. 그래서 상시 버튼 대신 가방 줄 → 확인 시트를 거친다.

### 탭-투-무브(대상 지향) 설계 근거

검토 결과는 `docs/meetings/2026-09-04-1150-폰-터치-조작-설계.md` §11.

- **조이스틱을 대체하지 않고 병행**한다. 짧은 미세 이동과 산책 감각은 아날로그가 낫고, 원거리 이동·목표 지향은 탭이 낫다.
- 단순히 "그 좌표로 걷기"가 아니라 **탭한 대상에 맞춰 동작**한다: 채집물 → 사거리(1.6)보다 조금 안쪽(1.1)까지 접근 후 자동 채집, 놓인 물건 → 접근 후 자동 줍기, 다른 캐릭터 → 대화 거리까지. 폰에서 가장 번거로운 "나무 옆 정확한 자리에 서기"가 이 방식으로 사라진다.
- 탭 판정 반경은 1.3 유닛(손가락이 뭉툭한 것과 옆 나무를 잘못 집는 것 사이의 타협).
- **수동 입력(방향키·조이스틱)이 들어오면 목표를 즉시 버린다** — 손으로 조작하는 중 캐릭터가 예전 목표로 끌려가면 조작을 빼앗긴 느낌이 된다.
- 목표 지점에는 바닥 마커를 표시한다. 없으면 "눌렀는데 반응이 없다"고 느낀다.
- 조이스틱 영역(좌하단)에서도 **끌지 않은 짧은 탭은 이동 지시로 흐른다.** 판정은 뗄 때 한다: 이동 12px 미만 + 누름 250ms 미만 + 이동 벡터가 한 번도 생기지 않음. 세 조건이 다 필요하다 — 시간만 보면 느리게 조금 끈 것이 탭이 되고, 거리만 보면 손가락을 대고 가만히 있다 뗀 것(중립 유지)이 탭이 된다.
  - 손가락을 **대는 순간** 오는 마우스 에뮬레이션 클릭은 여전히 버린다(`tapBranch=stick_area`). 그것까지 받으면 조이스틱을 끌기 시작할 때마다 시작점으로 이동 지시가 들어간다 — 예전에 스틱 영역 탭을 전부 버린 이유가 이것이고, 그 대가로 화면 왼쪽 아래 1/4이 조작 불가였다.
- **아직 충돌체가 없어서 직선 이동으로 충분하다**(나무도 통과 가능). 장애물을 넣는 시점에 내비게이션이 필요해진다 — 이 비용이 여기 잠재해 있다.
- 정밀 배치(꾸미기 P6에서 가구 놓기)는 탭 이동으로 안 된다. 그때 별도 UI가 필요하다.

**키보드와 터치는 병행**한다. 두 입력을 합산하지 않고 **크기가 큰 쪽**을 쓴다 — 합산하면 둘을 같이 쓸 때 속도가 두 배가 된다.

### 바위 조형물과 우회 이동

- 바위는 `data/world.json`의 `obstacles[]`(중심 `x`/`z` + `radius` + `style`)가 단일 출처다. 항목을 추가하면 바위·충돌·우회가 함께 늘어난다.
- **판정은 원 하나**다. 보이는 모양(`style: cluster`는 덩어리 3개)은 여러 개여도 판정 원 안에 들어오게 만든다 — 보이는 것과 판정이 다르면 "분명히 비켜 갔는데 걸린다"는 느낌이 생긴다.
- **탭 이동은 직선이 막히면 짧은 쪽으로 돌아간다**(`scripts/path_planner.gd`):
  - 막는 원에 **접선으로 올라타 호를 따라 돌아** 반대편 접점에서 목표로 향한다. 좌우 두 방향을 모두 계산해 **총 이동거리가 짧은 쪽**을 고른다.
  - 처음에는 원 중심을 선분에 투영해 좌우로 밀어낸 경유지 하나만 썼는데, (a) 출발/목표로 향하는 구간이 모서리를 스쳐 원을 파고들고 (b) 좌우 후보가 대칭이 되어 "짧은 쪽" 판정이 무의미해졌다 — `tests/test_path.gd`가 두 결함을 모두 잡아냈다.
  - 호는 40° 이하로 쪼갠다. 긴 호를 직선(현)으로 자르면 그 현이 원을 파고든다.
  - 우회 반복은 4회, 호는 10점으로 상한을 둔다 — 배치가 나쁠 때 무한 루프가 되지 않게. 상한에 걸리면 목표로 직진한다(이동 자체를 포기하면 "탭이 먹지 않는다"고 느낀다).
- **수동 이동(방향키·조이스틱)은 우회하지 않고 밀려난다** — 바위 표면 밖으로 되돌리는 방식이라 바위에 붙어 미끄러지듯 지나간다. 이동을 아예 막으면 조작이 답답하다.
- **왜 내비메시가 아닌가**: 장애물이 원뿐이고 수가 적어 접선 계산으로 정확히 풀린다. 다각형 장애물(건물·울타리)이 생기면 `NavigationServer3D`로 교체한다.
- ⚠️ **서버는 바위를 모른다**. 위치 검증은 경계·속도 상한만 보므로(`docs/protocol.md` §3) 조작된 클라이언트는 바위를 통과할 수 있다. 결과가 걸린 상호작용을 붙일 때 함께 다뤄야 한다.

### 캐릭터끼리 겹치지 않기

- 두 캐릭터는 **0.8 유닛보다 가까워지지 않는다**(`Player.SEPARATION`). 스프라이트 폭보다 좁게 잡아 대화할 만큼은 붙을 수 있게 했다.
- 겹침은 **가만히 있을 때도** 푼다 — 모두 같은 지점에서 시작하고, 남이 걸어와 겹치는 경우도 있다. 다만 한 프레임에 밀리는 양을 제한해(초당 2.5) 상대가 튀어 보이지 않게 한다.
- 겹침을 푼 뒤 다시 바위 밖으로 밀어낸다 — 상대를 피하다 바위 안으로 들어가는 것을 막는다.
- **서버는 접속 순서에 따라 스폰 지점을 링 위로 흩어 놓는다**(반지름 1.3, 8자리, 결정적). 그러지 않으면 새 캐릭터가 모두 한 점에 쌓인다.
- 각 클라이언트가 **자기 자신만** 밀어낸다. 양쪽이 각자 그렇게 하면 대칭적으로 떨어진다. ⚠️ 서버는 겹침을 검증하지 않으므로 조작된 클라이언트는 겹칠 수 있다 — 보기의 문제라 감수한다.

### 채팅 말풍선

- **둥근 모서리 + 연분홍 테두리 + 아래 꼬리**를 가진 말풍선을 글자 뒤에 깐다. 배경 없이 밝은 지형 위에 글자만 두면 읽기 어렵고, 각진 사각형은 톤에 맞지 않는다.
- 배경은 `QuadMesh`가 아니라 **코드로 그린 텍스처**(`scripts/bubble_texture.gd`)다 — 사각 메시로는 둥근 모서리를 만들 수 없고, 9-slice로 늘리면 모서리가 찌그러진다. 글자 크기에 맞는 텍스처를 만들고 **크기별로 캐시**한다(짧은 문장이 반복되므로 몇 개면 재사용된다).
- 밝은 배경 위에서는 글자 외곽선을 끄고 글자색을 어둡게 쓴다.
- 나무 뒤에 가려도 보이도록 `no_depth_test`로 항상 위에 그린다.

### 감정 표현 이모지 이펙트

- 이모지는 **말풍선과 별개 노드**로 크게(폰트 110) 떠서 **공중으로 날아오르며 사라진다**(1.5초, 커지며 흐려지고 좌우로 살짝 흔들림). 말풍선을 재사용하면 채팅 중에 감정을 표현할 때 말이 지워지고, 크기도 말풍선에 갇힌다.

### 감정 표현 이모지

- `data/emotes.json`의 `glyph`는 **이모지**다(😀😢😡😲❤️😴).
- 임베드한 Noto Sans KR에는 이모지 글리프가 없어 그대로 두면 전부 두부(□)가 된다. `scripts/fonts.gd`가 시작 시 기본 테마 폰트의 `fallbacks`에 **Noto Emoji(흑백, 864KB)** 를 붙인다.
- 컬러 이모지(Noto Color Emoji)는 수십 MB라 첫 로딩에 그대로 얹히므로 쓰지 않는다.

### 하단 접속자 바

지금 이 월드에 누가 있는지 화면 하단에 **초상화 + 이름**으로 보여준다(내 캐릭터가 맨 앞, 이름 색으로 구분).

- 초상화는 각 캐릭터의 `PlayerSprite`가 런타임에 만든 프레임(`idle_down` 0번)을 그대로 재사용한다. 초상화를 따로 그리면 외형이 바뀔 때 두 곳을 고쳐야 하고 프리셋이 늘 때마다 어긋난다.
- 인원이 많으면 좁은 화면 4명 / 넓은 화면 8명까지 보이고 나머지는 `+N`으로 접는다.
- 배경은 **내용 크기만큼만** 차지한다(하단 중앙). 화면 가로를 다 덮으면 월드를 가린다.
- 바 전체가 입력을 흘려보낸다(`MOUSE_FILTER_IGNORE`) — 화면 하단을 가로지르므로 입력을 먹으면 그 위를 탭했을 때 이동이 되지 않고, 조이스틱 영역과도 겹친다.

### 다른 창에 갔다 돌아올 때 (재동기화)

다른 탭·앱에 갔다 오면 브라우저가 프레임을 멈춘다. 돌아온 순간 내 캐릭터는 옛 위치에 있고, 남들은 멈춰 있고, 남이 주워간 물건이 아직 남아 있다. 그 상태로 조작하면 어긋남이 생긴다.

- **감지**: 웹은 `visibilitychange`로 "800ms 이상 숨겨졌다 돌아온 경우"만 센다(`web/shell.html`의 `afResumeToken`, 게임이 0.5초 간격으로 폴링). 창 포커스(blur/focus)로 판단하면 **채팅 입력창을 닫는 것만으로도** 재동기화가 걸려 방금 지시한 이동이 서버 위치로 되돌려진다(실측). 데스크톱은 포커스 알림 + 떠나 있던 시간으로 판단한다.
- **동작**: `resync`로 서버 상태를 다시 받고(`welcome`+`snapshot`), 내 캐릭터는 순간이동이 아니라 **걸어가서** 서버 위치에 맞춘다. 그 동안 화면을 살짝 흐리고 진행 표시를 띄우며 조작을 막는다(`scripts/resync_overlay.gd`).
- **블러**: 웹에서는 캔버스에 CSS `filter: blur(3px)`을 건다(Godot에서 전체화면 블러는 셰이더가 필요하지만 웹에서는 한 줄이면 된다). 웹이 아니면 반투명 판으로 대체한다.
- **안전장치**: 6초가 지나면 서버 응답이 없어도 오버레이를 걷는다 — 화면이 영구히 잠기는 쪽이 더 나쁘다.

### 소프트 키보드가 올라올 때

폰에서 채팅 입력을 열면 키보드가 화면 아래를 덮어 캐릭터가 가려진 영역에 들어간다. `ChatInput`이 `window.visualViewport`로 **실제로 보이는 높이**를 읽어(`window.innerHeight`는 키보드가 올라와도 그대로라 쓸 수 없다) 가려진 비율을 알리고, 카메라가 그만큼 내려가 **캐릭터가 보이는 영역의 중앙**에 오게 한다. 열려 있는 동안만 0.25초 간격으로 폴링한다(키보드가 올라오는 애니메이션 때문에 즉시 읽으면 0이 나온다).

### 아이템 이름 표시

월드에 놓인 물건의 이름표는 **주울 수 있는 거리(1.6)에 들어왔을 때만** 보인다. 항상 띄우면 물건이 많을 때 화면이 글자로 덮인다.

### UI 배율 — 1 UI 단위 = 1 CSS 픽셀 (`scripts/ui_scale.gd`)

폰 브라우저의 캔버스는 CSS 픽셀이 아니라 **기기 픽셀**로 잡힌다(DPR 2.6짜리 폰에서 폭 411 CSS px → 캔버스 1080px). 그런데 `canvas_items` 스트레치는 기준 해상도(960×540)에 대한 비율로 배율을 정하므로 배율이 1.12밖에 안 되고, 그 결과가 다시 DPR로 나눠져 **글자 14가 눈에는 CSS 6px**로 보였다(사용자 보고 "폰에서 글씨가 너무 작아", 2026-09-05 실측). 데스크톱은 DPR 1에 배율 2.0이라 같은 값이 28px로 보여서 드러나지 않았다.

- **보정**: `content_scale_factor = max(1, DPR / 스트레치배율)`로 DPR을 되돌려 **1 UI 단위 = 1 CSS 픽셀**이 되게 한다. 터치 버튼 크기(72/56/48)와 여백은 원래 CSS 픽셀 기준으로 잡은 값이라 이때 의도대로 맞는다. `max(1, …)`인 이유는 데스크톱을 지금보다 **작게** 만들지 않기 위해서다(DPR 1이면 항상 1이 되어 PC는 변화 없음).
- **글자만 추가로 키운다**: 논리 폭이 411px인 폰에서는 데스크톱과 같은 글자 크기가 화면 대비 훨씬 작게 느껴지므로, 좁은 화면에서 글자에 1.35를 곱한다(기본 16 → 21px). 배율 전체를 키우면 버튼·여백까지 커져서 좁은 화면을 다 먹는다.
- **글자와 함께 커져야 하는 것**: 글자를 담는 버튼 폭(`UiScale.dim`)과 접속자 바 초상화. 안 키우면 "스틱 OFF"가 잘리고 얼굴이 이름표보다 작아진다.
- **작은 버튼은 글자를 깎는다**: 48px 버튼에 21px 글자를 넣으면 "버림"이 "버"로 잘렸다 → 글자 크기를 버튼 폭의 1/2.6 이하로 제한한다.
- **패널은 화면 안으로 접는다**: 캐릭터 선택(560px)·가방(460px)처럼 데스크톱 기준으로 잡은 패널은 폰의 논리 폭(411px)을 넘는다 → `UiScale.panel_width`로 화면 폭에 맞춘다.
- DPR은 `devicePixelRatio`를 믿지 않고 **실제 캔버스를 재서**(`canvas.width / getBoundingClientRect().width`) 구한다. hidpi가 꺼진 빌드에서는 캔버스가 CSS 픽셀과 1:1이라 그대로 믿으면 두 번 보정한다.
- 회귀 판정은 모바일 E2E에 있다("UI 1단위가 CSS 1픽셀이다").

### 전체화면 버튼

+/− 바로 위에 둔다(사용자 요청). **전체화면도 소프트 키보드와 같은 제약을 받는다** — 브라우저는 `requestFullscreen()`을 사용자 제스처 핸들러 안에서만 허용하고, Godot 버튼의 `pressed`는 이미 그 제스처를 벗어난 다음 프레임이다. 그래서 키보드와 **같은 통로**(`window.afHotspots`)를 쓴다: 게임이 버튼 영역을 캔버스 비율로 알려주고 셸이 `touchend`/`click` 핸들러 안에서 직접 요청한다.

- **touchend 뒤에 오는 합성 click은 시계가 아니라 이벤트로 걸러낸다.** "300ms(또는 450ms) 안의 두 번째 이벤트는 무시" 식 가드는 합성 click의 지연이 메인 스레드 혼잡도에 좌우되기 때문에 새는데, 전체화면은 토글이라 새는 순간 한 번의 탭이 "켜고 바로 끄기"가 된다. touchend에서 플래그를 세우고 **다음 click 한 번만** 삼킨다(마우스 전용 브라우저는 touchend가 없어 영향 없음).
- 상태는 `fullscreenchange`로 셸이 기록하고(`window.afFullscreen`) 게임이 읽어 버튼 글자를 "전체화면"↔"창으로"로 바꾼다 — Esc나 브라우저 UI로 나가는 경우도 반영된다.
- 웹이 아니면(에디터·데스크톱) `DisplayServer.window_set_mode`로 직접 바꾼다.
- **지원하지 않는 브라우저에서는 버튼을 만들지 않는다.** 아이폰 사파리에는 Fullscreen API가 없어(비디오 전용 `webkitEnterFullscreen`만 있다) 눌러도 아무 일이 없다 — 셸이 `afFullscreenSupported`로 알려 주고 게임이 버튼과 핫스팟을 내린다. iframe에 `allowfullscreen`이 없는 경우도 같이 걸러진다. **지원 여부는 레이아웃을 잡기 전에 읽는다**: 다 만든 뒤 `visible`만 끄면 버튼이 있던 자리(약 60px)가 빈 채로 남아 그 아래 운동 버튼이 괜히 밀린다.
- **거절은 비동기로 온다.** `requestFullscreen()`은 Promise를 돌려주고, 정책·제스처 문제로 거절되면 그 Promise가 reject된다 — `try/catch`만 두면 가장 흔한 실패를 놓치고 콘솔에 uncaught rejection이 남는다(동기 예외는 사실상 API가 없을 때뿐이다). `.catch`로 받아 `afFullscreenLastError`에 남긴다. webkit 계열은 Promise를 돌려주지 않으므로 존재 확인이 필요하다.
- **모달이 떠 있으면 핫스팟을 지운다.** 가방 화면·시트는 화면 전체를 덮는 버튼으로 뒤를 막는데, 핫스팟이 남아 있으면 그 위를 탭할 때 셸이 먼저 전체화면을 토글해 "가방 닫으려다 전체화면이 켜진다". 채팅 핫스팟은 포커스라 멱등하지만 전체화면은 토글이라 문제가 된다.
- `JavaScriptBridge.eval`은 **숫자·문자열·불리언만 변환한다**(배열/객체는 null). 상태와 지원 여부를 한 번에 읽으려고 배열로 받았다가 분기가 아예 실행되지 않았다 — 비트로 합쳐 숫자로 받는다.
- **HUD 글자 상자의 폭을 버튼 열 왼쪽까지로 정한다.** 안내문이 가장 긴 줄이라 같은 y대에서 버튼 밑을 지나는데, "문장을 짧게 줄였으니 괜찮다"는 논리 폭에 의존하는 가정이다 — 사용자가 +로 화면을 키우면 논리 폭이 줄어 다시 겹친다. 폭이 정해지면 세 가지가 같이 풀린다: 겹침이 구조적으로 불가능해지고, 안내문을 **두 줄로 접을 수 있고**(`AUTOWRAP_WORD_SMART` + `max_lines_visible = 2` + `OVERRUN_TRIM_ELLIPSIS` — 잘라내기만 하면 문장 뒤쪽이 표시 없이 사라져 사용자는 잘린 줄도 모른다), 운동 버튼 열이 글자 블록을 피해 내려갈 필요가 없어진다(그 안전장치는 이미 두 화면 크기에서 다 죽은 항이었어서 회복한 세로 예산은 0이다 — 정리일 뿐이다).
- **상한은 자동으로 걸리지 않는다.** Godot의 `Control`은 크기를 항상 최소 크기로 클램프하고, 자동 줄바꿈·트리밍이 없는 `Label`의 최소 폭은 **글자 전체 폭**이다 — 그러면 긴 이름이나 아이템 종류가 늘어난 가방 줄 때문에 상자가 상한을 넘겨 늘어나고, 안내문도 그 폭을 받아 접히지 않는다. 세 줄 모두 `OVERRUN_TRIM_ELLIPSIS`를 켜서 최소 폭을 1로 떨어뜨려야 상한이 실제로 먹는다.
- **가방 줄의 히트박스 폭은 글자 폭을 재서 정한다**(`SIZE_SHRINK_BEGIN` + `custom_minimum_size.x` = `font.get_string_size(...)`, 상한은 상자 폭). VBox 자식은 상자 폭까지 늘어나므로 그대로 두면 데스크톱에서 700px 넘는 띠가 위쪽 월드 탭을 다 먹고, 최소 폭이 1인 채 SHRINK만 걸면 1px로 죽는다. 상수(예: 300px)로 자르면 그 값이 **표시 폭**까지 되어 아이템 종류가 늘면 뒤가 말줄임표로 사라진다 — 재면 둘 다 피한다.
- **좁은 화면 판정에 딸린 자리·크기는 전부 한 함수(`_apply_hud_layout`)가 잡고, 빌드와 리사이즈가 그 함수를 같이 쓴다.** 글자 폭·높이·폰트만 갱신했더니 채팅 로그·접속자 바·기술 버튼 열은 데스크톱 배치로 남아 겹쳤다(교차검증에서 claude·gemini가 같이 지적). 두 경로가 갈리면 "빌드 시점 판정에 의존하는 가정"이 다시 생긴다.
- 배치를 바꿀 때 **오프셋은 두 분기 모두 명시한다.** `set_anchors_preset`은 앵커만 바꾸고 이전 분기가 넣은 오프셋을 남기므로, 한쪽만 쓰면 좁혔다 넓혔을 때 되돌아오지 않는다(실측: 접속자 바가 왼쪽에 남았다). 회귀는 `npm run test:browser`가 창을 960→420→960으로 바꿔 접속자 바 x좌표로 판정한다. 상자 폭 상한·안내문 높이·안내문 폰트는 전부 좁은 화면 판정에 딸려 있고, 그 판정은 런타임에 뒤집힌다(창을 세로로 줄이거나 전체화면을 오가면 CSS 짧은 변이 480을 가로지른다). 빌드 시점에 굳히면 "논리 폭에 의존하는 가정"이 "빌드 시점 판정에 의존하는 가정"으로 옮겨갈 뿐이다.
- **넘치는지는 재서 판단한다.** 안내문은 활동·이모티콘 개수를 보간하므로 길이가 고정이 아니다 — `get_line_count()`가 상한(2줄)을 넘으면 짧은 문장으로 내린다. "문장을 두 줄에 맞춰 뒀다"는 주석은 배율이 바뀌면 거짓이 된다.
- **안내문은 높이를 예약해야 한다**(`custom_minimum_size.y = 두 줄`). autowrap과 트리밍을 같이 켜면 `Label`의 최소 크기가 (1, 1)이 되고, `max_lines_visible`은 높이를 예약해 주지 않아 라벨이 1px로 접힐 수 있다.
- 회귀 판정은 `npm run test:safari`(미지원 경로)와 `npm run test:mobile`(지원 경로: 상태 훅·핫스팟·모달 중 제거·탭 요청)에 나뉘어 있다. 헤드리스 WebKit은 미지원을 보고하므로 사파리 테스트만으로는 **버튼이 실제로 동작하는지 아무도 확인하지 않는다.** **"브라우저가 전체화면을 허용했는지"가 아니라 "제스처 안에서 요청했는지"로 판정한다** — 허용 여부는 환경(헤드리스·iOS 정책)에 따라 다르고, 우리가 지킬 수 있는 것은 호출 지점까지다.

### 오른쪽 위 버튼 열의 순서

위에서 아래로 **연결 상태 → 전체화면 → 크기(−/+) → 운동 버튼**. 전부 연결 상태 라벨 아래에 차례로 쌓는다. HUD 글자 블록을 피해 내려가지 않는다 — 글자 상자 폭이 이 열 왼쪽까지로 제한돼 서로 만나지 않기 때문이다. 한때 글자 블록(4.8줄) 아래로 내렸는데, 세로 예산을 먹어 창이 짧거나 배율이 높으면 마지막 버튼이 잘렸다. 전체화면이 미지원이면 크기 줄이 그 자리를 쓴다.

### 화면 크기 조절 (+/− 버튼)

자동 보정(1 UI 단위 = 1 CSS 픽셀)은 "읽을 수 있는 크기"까지만 맞춰 준다. 화면과 눈은 사람마다 달라서, **사용자가 직접 키우고 줄일 수 있는 +/− 버튼**을 오른쪽 위(연결 상태 라벨 아래)에 둔다.

- `content_scale_factor` 하나에 사용자 배율을 곱한다 — 글자·버튼·HUD·접속자 바가 **한꺼번에** 커지고 작아지고, 레이아웃을 다시 만들 필요가 없다.
- 범위는 0.7~1.8배(0.1 단계). 0.5는 폰에서 읽을 수 없고, 2.0을 넘으면 버튼 몇 개가 화면을 다 덮는다.
- 세이브의 `settings.ui_zoom`에 남겨 다음 접속에도 유지한다(기기별 취향이므로 슬롯이 아니라 세이브 전역).
- 좁은 화면 판정(`is_narrow`)은 **CSS 픽셀 기준**이라 배율을 바꿔도 흔들리지 않는다 — 배율에 따라 폰/데스크톱 레이아웃이 오갔다면 버튼을 누를 때마다 화면 구성이 바뀌었을 것이다.

### 좁은 화면 대응

- HUD는 **앵커/마진 기반**이다. 절대좌표를 쓰던 시절에는 폰 세로(412×839)에서 접속 상태 라벨이 화면 밖으로 잘렸다.
- 좁은 화면 판정은 **CSS 픽셀 기준의 짧은 변 < 520px**이다(가로로 돌린 폰도 높이가 411px이다). 예전에는 Godot 뷰포트 폭으로 판정했는데, 스트레치가 논리 폭을 항상 960 이상으로 유지해서 **폰에서도 판정이 계속 false였다** — 채팅 위치·접속자 수 제한 같은 폰 보정이 전부 죽어 있었다(2026-09-05).
- 좁은 화면에서는 채팅 로그를 6줄 → 3줄로 줄이고 화면 아래쪽으로 옮긴다(캐릭터를 가리지 않게).
- 좁은 화면 HUD는 이름·벨을 첫 줄, 시각을 그 아래 줄로 나눈다. 한 줄에 두면 오른쪽 상단의 연결 상태 라벨과 겹쳤다. 날짜도 연도를 뺀다.
- 접속자 바는 폰에서 **하단 중앙이 아니라 조이스틱 토글 위 왼쪽**에 둔다(3명까지). 하단 중앙은 오른쪽 버튼 무리와 왼쪽 조이스틱 토글 사이라 양쪽과 겹친다.
- 조작 안내 문구는 터치/키보드에 맞춰 다르게 나온다 — 폰에서 "[방향키] 이동"은 오히려 터치 UI를 못 찾게 만든다.
- 직교 카메라 `size`는 세로 기준이라 세로 모드에서 가로 시야가 급격히 좁아진다. 기준 비율(16:9)보다 좁아진 만큼 `size`를 키우고(최대 1.8배) 화면 회전 시 다시 계산한다.
- 터치 환경에서는 방향광 그림자를 끈다(WebGL2에서 발열·프레임 드랍의 주 원인). 캐릭터 접지감은 발밑 타원 데칼이 담당하므로 유지된다.

### 텍스트 입력과 모바일 키보드 (특히 사파리)

**iOS 사파리는 `focus()`가 사용자 제스처 핸들러 안에서 호출될 때만 소프트 키보드를 띄운다.** 안드로이드 크롬은 더 관대해서 이 차이가 오래 드러나지 않았다(사용자 보고 2026-09-05: "사파리에서 텍스트 입력할 때 키보드가 안나와"). 두 입력 경로를 각각 다르게 고쳤다.

- **이름 입력**: Godot `LineEdit`은 웹에서 OS 키보드를 띄우지 못한다. 그래서 **실제 `<input>`을 필드 위에 겹쳐 둔다** — 사용자가 그것을 직접 탭하므로 브라우저가 제스처를 그대로 인정한다. Godot 쪽 LineEdit은 자리와 모양만 잡고 `editable = false`로 둔다(둘 다 편집 가능하면 글자가 두 곳에 따로 들어간다). 화면 회전으로 자리가 바뀌므로 매 프레임 위치를 맞춘다.
- **채팅**: 버튼이 캔버스 안에 그려져 있어 탭 → Godot 신호 → GDScript의 `focus()`는 이미 제스처를 벗어난 다음 프레임이다. 그래서 게임이 **버튼 영역을 캔버스 비율(0~1)로 셸에 알려주고**(`window.afTextHotspots`), 셸(`web/shell.html`)이 `touchend` 핸들러 안에서 직접 포커스를 준다. 비율로 주는 이유는 셸이 DPR·스트레치 배율을 몰라도 되게 하려는 것이다.
- 입력창 글자 크기는 **16px 이상**이어야 한다 — 그보다 작으면 iOS가 포커스 시 화면을 확대해 레이아웃이 어긋난다.
- 회귀 판정은 `npm run test:safari`(WebKit)에 있다. 헤드리스에서는 실제 키보드가 뜨지 않으므로 **브라우저가 요구하는 조건**(제스처 안에서 그 `<input>`이 `document.activeElement`가 되는지)으로 본다.

### 채팅 입력 방식

웹에서는 **캔버스 위에 실제 DOM `<input>`을 얹는다**(`scripts/chat_input.gd`). Godot의 `experimental_virtual_keyboard`를 쓰지 않는 이유는 모바일 브라우저에서 **한글 IME 조합이 풀리거나 글자가 중복 입력되는** 사례가 보고돼 있기 때문이다(회의 §9-나). DOM 입력은 브라우저 네이티브라 OS 키보드·IME와 그대로 연동되고, IME 조합 중의 Enter(`isComposing`)는 전송으로 취급하지 않는다.

웹이 아닌 환경(에디터/데스크톱)에서는 같은 파일이 Godot `LineEdit`으로 갈라진다.

## 6-A. 운동장 (트랙 · 축구장 · 운동 5종)

섬 가운데를 운동장이 차지한다. **트랙과 축구장의 크기는 각각 240.83**(처음 지정한 "섬 면적의 1/6" = 50.7×28.5 기준)이고, 이 크기는 그대로 유지한 채 **섬만 각 변 1.5배(76.05×42.75)로 키웠다** — 운동장이 들어오자 걸어 다닐 곳이 좁다는 요청이었고, 운동장을 함께 키우면 비율이 그대로여서 문제가 해결되지 않는다. 그래서 지금 운동장은 섬의 약 1/13씩을 쓴다(둘 합쳐 15%). 가운데 통로(약 17유닛)와 남·북 띠(각 14유닛)가 넓어졌고, 킥보드는 거기서도 탈 수 있다.

숫자는 `data/world.json`의 `playground`와 `data/activities.json`이 단일 출처다 — **서버도 같은 파일을 읽는다**(활동별 속도 상한, 공 물리, 골 판정).

### 트랙 — 달걀 모양, 바깥은 초록·안쪽은 빨강

- 사용자 지정: **바깥 둘레가 초록(자전거), 안쪽이 빨강(인라인).** 두 레인 사이와 바깥에 흰 선을 넣어 "트랙"으로 읽히게 한다.
- 달걀 모양은 `z` 반지름을 각도에 따라 줄여 만든다(`(1 - egg*cos θ)`) — 정타원보다 한쪽 끝이 좁아 트랙처럼 보인다.
- 레인 경계는 **반지름 비율**로 자른다. "바깥에서 2.2유닛"으로 자르면 타원이라 각도마다 폭이 달라져 레인이 울퉁불퉁해진다.
- 텍스처가 아니라 메시(`SurfaceTool` 링)로 만든다: 21×14유닛을 덮는 텍스처는 크고, 확대하면 레인 경계가 뭉개진다. 링 하나가 삼각형 몇십 개라 폰에서도 부담이 없다.
- 트랙·축구장 자리에 있던 바위와 채집물은 밖으로 밀어냈다. **채집물은 인덱스를 유지하고 좌표만 옮겼다** — 인덱스가 바뀌면 세이브에 저장된 "이미 캔 채집물" 상태가 다른 자리에 붙는다.

### 운동 5종 — 버튼으로 켜고, 다시 눌러 끈다

| 운동 | 속도 | 어디서 | 특징 |
|---|---|---|---|
| 줄넘기 | 1.4 | 운동장 | 제자리 운동이라 느리다. 기술 4종(모아 뛰기·이중 뛰기·토드·엇걸어 풀어 뛰기) |
| 축구 | 4.4 | 운동장 | 골대·공이 나오고 차서 넣거나 패스한다 |
| 자전거 | 7.6 | 운동장 | 트랙 바깥(초록) 레인, 페달을 밟는다 |
| 인라인 | 6.6 | 운동장 | 트랙 안쪽(빨강) 레인, 상체를 기울인 자세 |
| 킥보드 | 6.0 | **어디서나** | 바퀴 두 개. 운동장 밖에서도 탄다(사용자 지정) |

- 버튼은 **운동장에 들어가면 나타난다.** 밖에서는 어디서나 탈 수 있는 킥보드만 보인다.
- 같은 버튼을 다시 누르면 원래 모습으로 돌아온다. 하고 있는 운동은 버튼에 `▣`로 표시한다.
- **운동 중에도 이동할 수 있다**(사용자 요청). 운동마다 속도가 다르고, 그 값은 서버가 이동 상한으로도 쓴다 — 클라이언트만 빠르면 서버가 계속 위치를 되돌린다.
- 운동장에서만 하는 운동은 **운동장을 벗어나면 자동으로 끝난다.** 트랙 밖으로 자전거를 타고 섬을 돌아다니는 것은 의도가 아니다.
- 버튼은 오른쪽 위 여백에 세로로 쌓는다. 왼쪽 아래는 조이스틱, 오른쪽 아래는 액션 버튼 무리라 화면에서 비어 있는 자리가 거기뿐이다.

### 운동하는 모습 — 몸을 그린 뒤 장비를 덮어 그린다

`scripts/player_sprite.gd`는 32×40 픽셀을 코드로 그린다. 운동 모습을 방향마다 새로 그리면 4방향 × 6프레임 × 5종을 손으로 관리해야 하므로, **기존 몸을 다 그린 뒤 장비와 자세를 덮어 그린다.**

- 자전거·킥보드는 다리 자리를 장비가 차지해야 "타고 있는" 것으로 보인다 → 그 영역을 지우고 다시 그린다.
- 줄넘기는 몸을 위로 올린 뒤(뛰어오르기) 줄을 **땅 기준**으로 그린다. 줄이 몸과 함께 올라가면 줄을 넘는 것으로 보이지 않는다.
- 왼쪽은 오른쪽 프레임을 좌우 반전한 것이라 오른쪽/앞·뒤 두 갈래만 그린다.
- 실측으로 고친 것: 어두운 바퀴를 어두운 신발·발판 위에 그리면 한 덩어리로 보인다 → 바퀴를 **밝게, 발판보다 먼저** 그리고 발판을 위에 덮는다. 인라인 부츠는 붙여 놓으면 널빤지 한 장으로 보인다 → 사이를 띄운다.
- 줄넘기는 **제자리에서도 애니메이션이 돌아야** 한다 → 줄넘기일 때만 idle도 6프레임 반복으로 만든다(자전거는 멈추면 정지 자세가 맞다).

### 축구공 — 서버가 소유한다

- 공의 위치·속도·골 판정은 **서버**가 갖는다. 각 클라이언트가 자기 화면에서 굴리면 기기마다 공이 다른 곳에 있게 되고 "내 화면에서는 골"이 된다.
- 공은 축구를 하는 사람이 있을 때만 존재한다(사용자 요청: "축구 버튼을 누르면 골대와 공이 나와"). 아무도 안 하면 치운다.
- **차기**: 액션 버튼(폰)·Space(PC)로 바라보는 방향으로 찬다. 공을 탭하면 공까지 걸어가서 찬다. 다른 플레이어를 향해 서서 차면 그게 패스다.
- **드리블**: 걸어가 공에 닿으면 살짝 밀린다. 차기만 있으면 걸어가 부딪혔는데 공이 가만히 있어 공처럼 보이지 않는다.
- 골라인을 넘고 골대 폭 안이면 골 → 공을 중앙으로 돌리고 모두에게 알린다. 폭을 벗어난 공은 튕긴다(섬 밖으로 나가면 주우러 갈 수 없다).
- 실측으로 고친 것: 공까지 걸어가 **도착 즉시** 차면 서버가 "너무 멀다"고 거절했다 — 이동이 10Hz로 묶여 나가 서버는 100ms 전 좌표를 갖고 있었다. 차기 전에 좌표를 확정 전송한다(`flush_move`).

## 6-A-1. 달리기 경주 (P5 첫 미니게임 — 판정을 서버로 옮긴 첫 사례)

운동장에 운동 5종이 있지만 **승패가 없었다**. 경주는 규칙이 한 문장("트랙 2바퀴, 먼저 들어오면 승")이라 설명이 필요 없고, 이미 있는 자전거(7.6)·인라인(6.6) 속도 차이가 그대로 전략이 된다.

### 서버가 상태 기계를 소유한다

`idle → lobby(10초) → countdown(3초) → running(최대 90초) → finished(15초) → idle`

- `race_join`은 **운동장 존 안에서만** 받는다 — 섬 반대편에서 참가하면 출발선까지 순간이동하거나 시작하자마자 실격이다.
- 진행 중(`countdown`/`running`)에는 새로 참가할 수 없다(`race_busy`).
- 아무도 안 남으면 **즉시 idle로 되돌린다** — 빈 대기실이 카운트다운을 시작하면 지나가던 사람이 영문 모를 숫자를 본다.
- 상태 방송은 **국면과 주행 진행이 바뀔 때만** 한다. 남은 시간까지 보내면 10Hz 방송이 되므로, 클라이언트가 받은 값에서 자기 시계로 센다(절대 시각을 주면 기기 시계 차이만큼 어긋난다).

### 체크포인트는 트랙 중앙선 위에, 순서대로만

- **8개**를 중앙선 위(45°마다)에 두고 반경을 **레인 반폭 이내(2.0)**로 제한한다. 4개(마름모)로는 인필드를 직선으로 가로지르는 것이 한 바퀴당 **9% 짧아서**(둘레 44.8 vs 40.7) "트랙을 안 도는 것"이 최적 전략이 됐다 — 8개면 3%로 줄어든다.
- 그것만으로는 부족해서 **밴드 이탈**도 본다: 두 체크포인트 사이에 트랙 밖(레인 안쪽 경계보다 안)으로 나가면 다음 통과를 인정하지 않고, 밴드로 돌아와 체크포인트에서 떨어지면 풀린다. 체크포인트 반경 검사만으로는 "지점 8곳을 찍는 최단 경로"가 여전히 인필드를 지날 수 있다.
- **밴드 판정은 달걀 왜곡을 보정해야 한다.** 트랙은 z가 `(1 − egg·cosθ)`로 늘어난 달걀 곡선이라 순수 타원비로 보면 최대 4.7% 오차가 나고, 그 최대점(남서쪽)이 체크포인트와 겹쳐 **실제 트랙 위인데 이탈로 판정**됐다 — 바깥 라인으로 그 코너를 도는 러너의 통과가 인정되지 않았다. 같은 각도의 곡선 반지름으로 나누면 오차가 0.35%로 떨어진다. 밴드 안쪽 경계 비율도 트랙 값에서 계산하지만 **유효범위를 강제한다**: 예전에는 무가드로 읽어 `NaN`이 되면 비교가 항상 false가 되고, 그러면 로그 하나 없이 모든 경주가 타임아웃 + 보상 0으로 끝났다.
- **다음 체크포인트만** 본다. 순서를 어긴 통과는 무시하고 되돌리지 않는다 — 되돌리면 트랙 밖으로 한 번 튀는 것만으로 순위가 뒤집힌다.
- 마지막 체크포인트에서 출발선(0번)에 도달하면 한 바퀴다. `cp == -1`에서의 0번 통과는 출발이므로 세지 않는다(별도 플래그를 두면 리셋을 빼먹는다).
- 좌표는 트랙 기하(`outer_a`·`outer_b`·`lane`·`egg`)에서 계산해 넣은 값이므로, **트랙을 고치면 이 값도 다시 계산해야 한다** — 서버 유닛 테스트가 중앙선에서 벗어났는지 검사한다.

### 보상과 방어

- 1위 300 / 2위 150 / 3위 50 / 완주 20벨. **참가자가 1명이면 완주 보상만** 준다 — 혼자 돌려 300벨을 반복해서 긁는 경로를 막는다.
- 참가비는 없다(진입 장벽을 만들 이유가 없다). 종료 후 15초 대기는 보상 연타를 막고 결과를 읽을 시간을 준다.
- **좌표는 여전히 클라이언트 주장이다.** 경주 중에는 상한을 조이고(1.6 → **1.25**) 클램프된 **초과 거리를 누적**해 3유닛을 넘으면 실격한다. 실제 취약점은 순간이동이 아니라 **상시 마진**이었다: 초과분은 거부가 아니라 클램프라서, 계속 상한을 밀어붙이는 클라이언트는 실격 없이 정직한 주행보다 60% 빨랐다(자전거 7.6 → 12.16). 누적을 보면 한 번의 순간이동과 상시 마진이 같은 기준으로 걸린다.
- **접속이 끊긴 참가자는 즉시 빼낸다.** `leave()`는 레코드를 남기므로(online=false) 그 러너가 굳은 좌표로 영원히 "달리는 중"이 되어, 완주자가 있어도 타임아웃 90초를 다 채웠고, 혼자 참가한 사람이 탭을 닫으면 운동장이 약 118초 잠겼다.
- **"혼자면 완주 보상만"의 기준은 "끝까지 함께한 참가자 수"**다(완주·실격했거나 아직 접속 중인 참가자). 세 가지를 동시에 만족해야 한다: 3명이 참가해 1명만 완주해도 우승자는 300을 받고(완주자 수 기준은 20벨을 줬다), "탭 두 개로 참가한 뒤 하나를 닫는" 편한 파밍은 막히고, **두 탭이 실제로 코스를 다 도는 경로는 남는다** — 토큰이 곧 신원이라는 신뢰 경계 안의 문제이고 수고 대비 벨이 낚시보다 낮다.
- 결과 국면(15초)에서는 마지막 참가자가 포기해도 **리셋하지 않는다** — 그 쿨다운이 보상 연타를 막는 장치다.
- 참가·포기도 500ms 간격 제한을 받는다(한 메시지가 전원 방송을 유발하는 경로다).
- **카운트다운 동안 출발선에 묶는다**(놀이기구 좌석과 같은 `rideAnchor`). 제약이 없으면 트랙 반대편에 있던 사람이 출발선까지 1/4바퀴를 더 가야 해서 순위가 그것으로 갈린다. 출발선 **직전**(0.9유닛 뒤)에 세우지만, 그것이 "첫 바퀴 공짜"를 막는 장치는 아니다 — 정렬 위치도 체크포인트 반경(2.0) 안이라 출발 첫 틱에 0번 통과가 인정된다. 첫 통과를 바퀴로 세지 않는 것은 `cp == -1`에서의 통과를 출발로 처리하는 규칙이다.

  **정렬 좌표는 클라이언트에도 내려보내야 한다.** 서버가 좌표만 바꾸면 화면의 내 캐릭터는 제자리에 남고(내 위치는 서버 방송으로 보정하지 않는다 — resync만 예외), 최대 11유닛 어긋난 채 출발해서 그 차이가 첫 이동에서 속도 초과로 잡혀 **출발과 동시에 전원 실격**된다. 놀이기구는 클라이언트가 좌석까지 걸어가서 앉으므로 이 문제가 없었다. 추가로 출발 후 1.2초는 초과 누적을 유예한다(정렬 적용이 한 틱 늦는 경우).
- 기록은 서버 시각 기준이다. 클라이언트 시계를 쓰면 기록이 조작된다.

### UI

- 운동장 안에서만 오른쪽 열에 `[경주]`(참가 중이면 `[경주 포기]`, 진행 중이면 비활성 `[경주 중]`).
- 존 라벨 한 줄이 곧 경주 UI다: 대기 인원·남은 시간 → 카운트다운 숫자 → `2바퀴 중 1 · 남은 시간 62초`(좁은 화면은 `1/2바퀴`) → 완주 시 `1등 · 24.3초`.
- 결과는 토스트 3줄(등수·기록·보상). 내 결과의 벨은 서버 값으로 맞춘다.
- 결승선만 체커 무늬다 — 나머지 체크포인트는 흰 선. **체커의 어두운 색은 전용 색(`finish_dark`)이어야 한다**: 골대 색(#eef1f2)은 선 색과 거의 같아 흰 막대 하나로 보였다(실측).
- 경주에 참가하지 않은 사람에게는 아무것도 강제하지 않는다 — 트랙을 계속 걸어도 된다(방해는 놀이의 일부).

### 회귀 판정

- 서버 유닛 16종: 존 검사, 상태 전이, 빈 대기실 즉시 종료, **체크포인트 순서 강제**, **인필드 횡단 무효**, 혼자 완주 시 완주 보상만, 둘이면 순위 보상, 타임아웃, 속도 누적 실격, 진행 중 참가 거절, **끊긴 참가자가 경주를 막지 않음**, 끊김으로 0명이면 즉시 idle, 결과 국면 쿨다운 유지, 보상 유효범위, 체크포인트 좌표·반경 린트.
- 브라우저(`npm run test:race`): 존 전용 버튼, 참가/포기, `lobby → countdown → running` 전이. **트랙 두 바퀴를 걷게 하지 않는다** — 90초를 먹고 카메라·타이밍에 취약해진다.

## 6-B. 놀이터 (모래 바닥 · 놀이기구 4종)

스폰 남쪽 빈 띠(17×9.6)에 **바닥이 모래인 놀이터**를 둔다(사용자 지정). 좌표·크기는 `data/world.json`의 `park`, 물리·연출 값은 `data/activities.json`의 `park`가 단일 출처다.

### 이 구조에서 무엇이 가능한지가 기구 선택을 정했다

**캐릭터에는 Y축이 없다** — `position.y`는 항상 0이고 서버도 2D로 검증한다. 그래서 높이는 전부 **스프라이트 오프셋**으로 표현하고, 타는 사람의 논리 위치는 좌석(또는 미끄럼틀 경로)에 붙어 있다. 등반·짚라인처럼 진짜 높이가 필요한 기구를 뺀 이유가 이것이다.

| 기구 | 조작 | 동기화 |
|---|---|---|
| 미끄럼틀 | 사다리를 탭 → 올라가 내려오고 **저절로 끝난다** | **없음** — 높이를 위치의 함수로 만들었다(`height_at`). 위치는 어차피 방송된다 |
| 그네 | 좌석을 탭 → 앉음, 액션 버튼으로 **더 높이** | 진폭만(activity의 `trick` = "자리:진폭"). 흔들림은 `f(시각)`이라 대역폭 0 |
| 뺑뺑이 | 테두리를 탭 → 탐, 액션 버튼으로 **밀기** | 각도를 **서버가 소유**(밀 때마다 속도가 바뀌어 시간 함수로는 못 맞춘다) |
| 시소 | 좌석을 탭 → 앉음, 액션 버튼으로 **내 쪽 누르기** | 기울기를 **서버가 소유**(스프링-감쇠). 각자 계산하면 누가 위인지 갈린다 |

### 버튼이 아니라 기구를 탭해서 탄다

운동장의 운동은 버튼이지만 놀이기구는 **그 자리에 가서 타는 것**이라, 탭-투-무브의 "대상을 탭하면 다가가서 자동 처리" 경로를 그대로 쓴다(`button: false`). 버튼으로 타면 기구에서 멀리 떨어진 자리에 앉게 되고, 서버가 그 자리를 좌석으로 고정해 공중에 앉은 것처럼 보인다. 타고 있는 동안 버튼 자리에는 **내리기** 하나만 남는다.

- 좌석까지는 **정확히** 걸어간다(대상 앞에서 멈추는 `_approach_point`를 쓰지 않는다) — 서버가 앉은 자리를 좌석으로 고정하기 때문이다.
- **자리는 서버가 배정한다.** 고른 자리가 찼으면 빈 자리로 옮기고, 없으면 거절한다(`seat_taken`). 클라이언트가 정하면 두 사람이 같은 좌석에 겹쳐 앉는다.
- 앉아 있는 동안 서버가 위치를 좌석에서 0.6유닛 안으로 묶는다(`RIDE_LEASH`). 클라이언트도 방향 입력을 무시한다(`locked`) — 둘 다 필요하다: 클라이언트만 막으면 변조한 클라이언트가 앉은 채 섬을 돌아다닌다.

### 화면에서 보이도록 축을 골랐다

카메라가 55° 기울어 있어 **z 방향 움직임은 화면에서 눌려 보인다**. 처음에는 그네를 z로 흔들고 시소를 z축에 놓았는데 흔들리는지·누가 위인지 알아볼 수 없었다(실측). 그래서 **그네는 x축으로 흔들고(좌석은 z축으로 나란히), 시소는 x축에 놓았다**.

미끄럼틀 경사면은 오일러 각을 직접 계산하지 않고 `look_at_from_position`으로 "위 발판 끝에서 출구 바닥을 바라보게" 만든다 — 진행 방향과 경사를 각각 `atan2`로 넣으면 축 순서·부호에 따라 반대로 솟는다(실측).

### 남은 것

- 기구를 **장애물로 만들지 않았다.** 통과해 걸을 수 있다. 뺑뺑이 발판 반지름을 장애물로 잡으면 좌석(테두리)이 밀림 처리에 밀려 탑승이 깨진다 — 작은 픽셀 게임에서는 통과가 덜 나쁜 쪽이다.
- 그네 위상은 각 클라이언트의 시계를 쓴다. 시계가 크게 어긋난 기기 사이에서는 그네의 위상이 다르게 보인다(주기 운동이라 눈에 걸리지 않는 수준).

## 6-C. 낚시와 벌레잡기 (시간·계절이 처음 의미를 갖는 곳)

채집이 "나무를 탭한다" 하나뿐이면 섬을 돌아다닐 이유가 없다(가까운 나무만 반복). 낚시터(물가 8곳)와 벌레 스폿(꽃밭 10곳)에는 **장소 조건**과 **시간·월 조건**이 붙어서, "지금 저기 가야 하는 이유"가 생긴다. 우리에게는 이미 `GameClock`(현실 시간 = 게임 시간)이 있어 이 자극은 공짜로 얻는다.

### 무엇이 잡히는지는 서버가 정한다

`data/gatherables.json`의 `catch_tables`가 단일 출처다: 항목마다 `weight`(가중치), `hours`(`[시작, 끝)`, 시작 > 끝이면 자정을 넘는 구간), `months`(있으면 그 달만).

- **클라이언트는 아이템을 주장하지 않는다.** `gather`는 채집물 index만 보내고, 서버가 그 자리의 종류(`fishing`/`bug`)에 맞는 테이블을 자기 시계로 걸러 가중치 추첨한다. 클라이언트가 아이템을 고르면 기기 시계를 겨울 밤으로 맞춰 실러캔스(2500벨)만 반복해서 잡을 수 있다.
- **경계에 여유를 두지 않는다.** 클라이언트는 자기 시계로 "지금 잡히는 것"을 표시할 뿐이고 판정은 서버에서만 하므로, 여유(±30분 등)는 조건을 그만큼 느슨하게 만들 뿐이다. 표시는 `CatchTable`(클라이언트)이 같은 데이터를 읽어 **조건 밖이면 벌레 메시를 감추고 탭 대상에서도 뺀다** — 화면에 있는데 걸어가면 거절당하는 것이 가장 나쁘다. 꽃은 남으므로 탭 필터가 없으면 발밑에 두고 "조금 더 가까이 가야 합니다"가 무한 반복된다(`is_catchable_now()`를 `is_available()`과 나눈 이유). 두 시계가 다르면 서버가 이긴다.

  이 숨김은 **현재 데이터에서는 발동하지 않는다**(연중 종이 24시간·12개월을 덮으므로 항상 잡을 것이 있다). 미래 데이터(계절 전용 스폿·이벤트 한정 종)를 위한 안전망으로 남겨 두고, 시즌 판정이 필요 없는 종류는 `set_process(false)`로 검사 자체를 끈다.
- 어떤 종류가 테이블 구동인지도 **`catch_tables`의 키가 단일 출처**다. 클라이언트가 `["fishing","bug"]`를 하드코딩하면 세 번째 종류를 추가하는 순간 서버는 아이템을 비우고 클라이언트는 `"wood"`를 넣어 갈린다.
- **오프라인(서버 미연결)에서는 이 자리를 캘 수 없다.** 무엇이 잡히는지 모르므로 빈 아이템이 가방·세이브에 남고, 이름 없는 물건은 팔아서 지울 수도 없다.
- 조건에 맞는 항목이 하나도 없으면 `nothing_here`로 거절하고 **재생 쿨다운도 걸지 않는다** — 잡을 수 없는 자리에 벌을 줄 이유가 없다.
- 계절을 문자열("겨울")이 아니라 `months` 숫자로 둔 이유: 서버(JS)와 클라이언트(GDScript)가 같은 계절 매핑을 각자 구현하면 두 곳이 갈린다.

### 기대값을 시간대로 갈라 선택을 만든다

| 조건 | 가중치 합 | 기대값 |
|---|---|---|
| 낮(멸치 40 / 붕어 30 / 농어 18) | 88 | **124.5벨** |
| 밤·비겨울(멸치 / 농어 / 오징어) | 67 | **190.4벨** |
| 밤·겨울(+실러캔스) | 70 | **289.4벨** |

**실패율은 시간대와 무관하다** — 그래서 "밤에 낚시하러 나간다"가 선택이 된다. 실러캔스는 겨울 밤 가중치 3/70 = **4.3%**라 한 번 잡으면 사건이 된다(조개 14개분). 이 숫자는 밸런스 판단의 근거로 인용되므로 테이블을 고칠 때 함께 고친다.

**벌레는 연중 4종(낮: 무당벌레 60 / 애벌레 45, 밤: 나방 80 / 거미 110)을 깔고** 계절 한정 3종(나비·매미·장수풍뎅이)을 그 위에 얹는다.

- 계절 한정만 두면 9~2월에 벌레 스폿 10곳이 통째로 죽어서, 걸어가서 거절당하는 자리만 남는다(첫 구현이 그랬고, "겨울 밤 거절"을 정상으로 고정한 테스트 때문에 회귀로도 안 잡혔다).
- **연중 종은 흔한 것으로 둔다.** 거미(110)를 장수풍뎅이(400)와 같은 가중치로 두면 여름 밤 장수풍뎅이가 100% → 50%가 되어 "귀한 벌레"라는 감각이 사라진다. 낚시 테이블의 기울기(40 → 3)와 결을 맞춰 거미는 14로 낮췄다(여름 밤 장수풍뎅이 36%).
- 어느 월·시각에도 후보가 **2종 이상**이어야 한다 — 단일 뽑기는 "무엇이 잡힐까"가 없어 그냥 느린 채집이다.
- `hours`는 낮 `[6,19)`과 밤 `[19,6)`이 **24시간을 빈틈없이 덮어야 한다.** 밤을 `[19,5)`로 두면 05시대에 아무것도 나오지 않는 한 시간 구멍이 생긴다.
- 회귀 판정 3종이 이 불변식을 지킨다: 모든 월·시각에 최소 1종 / 후보 2종 이상 / **연중 항목만으로 24시간 커버**(계절 한정이 우연히 구멍을 메우는 상태를 막는다).

벨의 소비처는 아직 없으므로 이 단계에서 인플레이션은 문제가 아니다. 소비처(가구·집)가 붙는 시점에 낚시터 쿨다운(20초)과 가격을 다시 본다.

### 낚시는 타이밍이 있고 벌레는 없다

- **낚시터는 "그냥 캐기"로 우회할 수 없다.** 액션 버튼의 근처 채집 경로(`_try_gather`)는 종류를 보지 않고 가장 가까운 것을 캐므로, 낚시터 옆에서 버튼만 눌러도 대기·타이밍을 건너뛰고 물고기가 나왔다(리뷰 지적). 그 경로도 낚시 시작으로 넘긴다. 단 **조작된 클라이언트는 여전히 `gather`를 직접 보낼 수 있다** — 서버는 낚시라는 개념을 모르고 존재·재생·사거리만 본다. 타이밍은 재미 장치이고 방어선이 아니다.
- 낚시: 낚시터 탭 → 다가가서 자동으로 활동 켜짐 → **1.5~4초 무작위** 대기 → `!` → **1.2초 안에** 액션 버튼. 대기를 무작위로 두는 이유는 고정이면 초를 세게 되고 그러면 타이밍이 아니라 암기가 되기 때문이다.
- 실패(헛챔질·놓침)에는 쿨다운을 걸지 않는다. 실패의 벌은 시간 낭비로 충분하고, 서버는 애초에 채집 요청을 받지 않았으므로 자리도 그대로다.
- 벌레는 그물 한 번(기존 채집과 같은 즉시 처리). 스폿에 벌레가 없는 시간대(겨울 등)에는 서버가 거절한다.
- `button: false` 활동이라는 점은 놀이기구와 같지만, **놀이기구인지의 판정은 놀이기구 목록으로 한다**(`_park_ride_kinds`). `button:false`로 판정하면 낚시 중에 "내리기" 버튼이 뜨고 좌석·리시 처리까지 끌려 들어온다(실측). 낚시는 대신 "그만두기" 버튼을 둔다 — 폰에는 Esc가 없다.

### 회귀 판정

- 서버 유닛(`tests/server-world.test.mjs`): 시간·월 조건, 가중치 추첨의 결정성, 겨울 밤 벌레 거절 + 쿨다운 미적용, 테이블 항목이 전부 `items.json`에 있고 가격이 유효범위 안인지(데이터 린트), 빈 테이블에서도 서버가 뜨는지.
- 브라우저(`npm run test:fishing`): 낚시터 탭 → `wait` → `bite` → 채기 → 가방·획득 아이템, 헛챔질·놓침 경로.

## 6-D. 이웃 동물과 도감 (채집의 목적)

채집물의 소비처가 "판다" 하나뿐이면 가방은 벨 환전 창구다. 이웃 동물 3인이 **하루 1개씩 부탁**을 하고, 보상이 판매가보다 크면 "팔지 말고 남겨두는" 선택이 생긴다 — 이 게임에서 처음 생기는 의사결정이다.

| id | 이름 | 종 | 자리 | 말투 |
|---|---|---|---|---|
| `mochi` | 모찌 | 고양이 | 서쪽(-33, 10) | 느긋한 반말 |
| `dungdang` | 둥당 | 곰 | 남동쪽(31, -16) | 우렁차고 다정함 |
| `pparang` | 빠랑 | 오리 | 남쪽 물가(-8, -17.5) | 촐랑거림 |

빠랑을 낚시터 근처에 둔 이유: 낚시하러 가는 동선과 **자연히 만나게** 하려는 것이다.

### 무엇을 서버가 갖고 무엇을 클라이언트가 갖는가

- **위치와 배회는 클라이언트**: 배회는 시간 함수(`sin`/`cos`, 축마다 다른 주기)로 그린다. 서버가 NPC 위치를 소유하면 3마리 × 10Hz 브로드캐스트가 늘어나는데 얻는 것은 "모두 같은 자리에서 본다"뿐이다 — 그네와 같은 결정(§6-B). 기기 시계가 몇 초 달라도 "그 근처를 어슬렁거린다"는 사실은 같다.
- **부탁과 정산은 서버**: 어떤 부탁인지는 `(토큰, NPC, 날짜)`의 **결정적 해시**로 고른다. 재시작·재접속·스냅샷마다 같은 부탁이어야 하고("가져왔는데 다른 걸 요구한다"를 막는다), 그러면 부탁 상태를 따로 저장할 필요도 없다.
- **보상 = 판매가 × 개수 × `reward_multiplier`(1.8)를 서버가 계산한다.** 클라이언트가 금액을 주장하면 벨을 임의로 불릴 수 있다. 조개 2개 부탁이면 팔아서 360, 주면 648 — 부탁이 항상 유리하지만 **찾아야 하는 비용**이 있어 자동 선택은 아니다.
- **하루 1회는 서버 날짜로 판정한다.** 기기 시계를 넘겨 무한 반복하는 것을 막는다.
- **거리도 서버가 본다**(배회 반경 + 3.5). 없으면 섬 반대편에서 부탁만 눌러 벨을 받을 수 있다.
- 정의에 없는 아이템을 요구하는 부탁은 **로드할 때 걸러낸다** — 그 부탁은 영원히 완료할 수 없고 가격도 계산되지 않는다.
- **시간·월 제한이 붙은 아이템은 부탁으로 쓰지 않는다**(같은 자리에서 걸러낸다). 부탁은 하루 내내 고정이므로, 낮에만 나오는 매미를 부탁받으면 밤에 접속한 사람은 그날 아무것도 할 수 없다 — 9~5월이면 아예 불가능하다. 회귀는 데이터 린트가 막는다.
- **보상 편차도 관리한다**(최대/최소 3배 이내). 잡초 3개(54벨)와 조개 2개(648벨)가 섞이면 "팔지 말고 남겨두는 선택"이라는 의도가 잡초 날에는 성립하지 않는다.
- **모든 거절에 현재 부탁 상태를 함께 보낸다**(`npc_error`). 클라이언트는 버튼을 누른 즉시 잠그므로(연타 방지) 살리는 경로가 빠지면 회색 버튼으로 굳고, 세션을 켜둔 채 자정을 넘기면 어제 상태로 굳는다. 날짜가 바뀌면 서버가 접속자에게 `npc_state`를 한 번 밀어 준다.
- 실패한 정산도 간격 제한을 받는다 — 성공만 기록하면 `too_far`를 무한 연타할 수 있고 다른 핸들러와 규칙이 달라진다.

### UI

- 부탁이 남아 있으면 머리 위에 `!`. 화면 알림을 띄우지 않는 이유: 섬을 돌아다니다 **눈으로 발견하는** 편이 이 게임의 리듬에 맞다.
- 대화창은 **아래쪽 시트**다. 화면 중앙을 덮으면 말하는 상대가 가려진다.
- 부족할 때 **몇 개 부족한지 숫자로** 보여준다("나무! 2개! (0/2 있음)"). "부족하다"만 말하면 가방 화면을 왕복하게 만든다.
- 버튼은 조건이 충족될 때만 `[가져왔어]`이고, 아니면 `[알겠어]`다 — 같은 버튼을 두면 눌러도 아무 일이 없는 버튼이 된다.
- **동물은 배회하므로 탭 반경을 넓게(2.2) 잡는다.** 채집물과 같은 1.0으로 두면 눈에 보이는 동물을 탭해도 빈 땅 탭이 된다(실측).

### 도감

- 진입은 **가방 화면의 `[도감]`**이다. 최상위 버튼을 늘리면 오른쪽 위 열이 또 길어진다(세로 예산).
- 탭 두 개: **아이템**(획득 수·판매가, 미획득은 `???`)과 **이웃**(오늘 도운 사람, 진행 중인 부탁).
- 누적 수의 단일 출처는 **서버**(`dex`)다. 채집·줍기로 늘고 **판매·드랍으로 줄지 않는다** — 도감은 "무엇을 가졌는지"가 아니라 "무엇을 만났는지"의 기록이다.
- 미획득 이름을 감추는 이유: 다 보여주면 목록표가 되고 찾는 재미가 없다. 남은 칸 수는 요약 줄이 알려준다.
- 서버는 `dex` 전체를 매번 방송하지 않는다(**welcome·resync에만** 실린다 — 스냅샷에는 없다). 내가 캔 것은 클라이언트가 함께 올려 즉시 반영하고, 다음 접속에 서버 값으로 덮인다.
- **내가 버린 것을 내가 주우면 세지 않는다.** 버리고 줍기를 반복해 숫자를 올릴 수 있었다(월드 아이템에 버린 사람을 기록해 구분하고, 클라이언트도 같은 규칙을 쓴다 — 다르면 화면 도감만 올라가고 재접속에 되돌아간다).
  - **남은 경로**: 토큰은 클라이언트가 만들고 줍기에 거리 검사가 없으므로, 탭 두 개(토큰 A·B)로 A가 버리고 B가 주워 되돌리면 카운트를 계속 올릴 수 있다. 도감에는 보상이 걸려 있지 않아 그대로 두지만, 완성 보상을 붙이는 시점에는 "아이템별 최초 1회만 인정" 또는 "줍기는 세지 않음"으로 바꿔야 한다.

### 회귀 판정

- 서버 유닛 8종: 부탁 결정성, `unknown_npc`/`not_enough`(부족 수 포함, 가방 불변)/`already_done`/`too_far`/`rate_limited`, 정산 금액과 차감, 잘못된 부탁 아이템 필터, 도감 누적(판매·드랍에 줄지 않음), 재시작 후 진행도 유지.
- 브라우저(`npm run test:npc`): 동물 탭 → 대화창 → 부족 상태에서는 정산되지 않음 → 나무 2개 모아 오기 → 정산(벨 증가·상태 완료) → 도감 열기(아이템 칸·이웃 탭). 부탁은 **데이터 사본(`AF_DATA_DIR`)으로 나무 2개로 고정**한다 — 실제 데이터는 밤에만 나오는 물고기도 요구할 수 있어 테스트가 흐름을 끝까지 볼 수 없다.

## 6-E. 꾸미기와 토큰 이전

외형은 **자기 표현**이라 비용을 두지 않는다(무료·무제한). 다만 "언제든 바꿀 수 있음"을 알려야 애착이 생기므로, 캐릭터 선택 화면이 아니라 **월드 안에서** 바꿀 수 있어야 한다.

### 한 화면에 둔 이유

진입은 **가방 화면의 `[꾸미기]`**다(도감과 같은 결). 외형과 토큰 이전을 같은 화면에 둔 것은 둘 다 "내 캐릭터 자체"에 관한 것이고, 최상위 버튼을 늘리면 오른쪽 위 버튼 열이 또 길어지기 때문이다(세로 예산).

### 무엇을 서버가 갖는가

- 저장 형태는 **프리셋 위에 덮는 값**(`custom: {hair, skin, outfit}`)이다. 비어 있으면 프리셋 그대로이므로 세이브 마이그레이션이 필요 없다.
- **선택지(화이트리스트)의 단일 출처는 서버**이고, 그 목록은 `data/characters.json` 프리셋에서 유도한다. 팔레트 키를 전부 허용하면 `skin`에 `rope`를 넣을 수 있고, 코드에 목록을 박으면 프리셋을 늘려도 서버가 안 따라온다(확장 지점이 거짓말이 된다).
- 임의 문자열은 남의 클라이언트에서 색 조회에 실패해 기본색으로 떨어질 뿐 렌더가 깨지지는 않지만, 그 값이 **세이브에 남는다** — 그래서 서버가 거절한다.
- **스냅샷·join에도 `custom`을 싣는다.** 없으면 나중에 들어온 사람에게는 바뀐 외형이 안 보인다(놓치기 쉬운 부분이라 서버 테스트에 명시했다).
- 변경 간격은 500ms이고 **거절은 그 예산을 쓰지 않는다**(거절당한 뒤 곧바로 다시 시도할 수 있어야 한다).
- **오프라인에서 바꾼 외형은 세이브에 표시(`custom_pending`)를 남겨** 다음 접속에 흘려보낸다. 메모리 변수만 두면 "오프라인으로 바꾸고 탭을 닫았다가 서버가 살아난 뒤 다시 켜는" 흔한 경로에서 사라진다 — welcome이 서버의 옛 값으로 덮고 세이브까지 그 값이 된다.

### UI 원칙

- 고르는 즉시 내 캐릭터에 반영한다(**미리보기 = 실제**). 서버로 보내는 것은 `[닫기]`로 확정할 때 한 번뿐이다 — 색을 훑는 동안 방송을 도배하지 않는다. `[되돌리기]`는 열었을 때 상태로 복원한다.
- 견본 표시는 **프리셋에 커스텀을 덮은 "지금 외형"** 기준이다. 커스텀만 보면 아직 바꾼 적 없는 항목에 아무 표시가 없어서, 빨간 옷을 입고 있는데 어떤 견본도 선택돼 보이지 않는다(실측).
- **외형 재적용은 `setup()`이 아니라 `apply_look()`이다.** `setup()`은 값만 저장하고 색은 `_ready()`에서 한 번 계산되며 프레임은 (활동, 기술)별로 캐시된다 — 이미 트리에 붙은 스프라이트에 `setup()`을 다시 불러도 **아무 일도 일어나지 않는다**. 첫 구현이 그래서 색을 골라도 화면이 그대로였고, 서버 방송만 보는 테스트는 그걸 통과시켰다. `apply_look()`은 색을 다시 계산하고 캐시를 버리고 프레임을 다시 만들며, 하고 있던 활동은 유지된다.
- **접속자 바의 초상화도 스프라이트에서 뜬 것**이라 함께 갱신한다(월드의 캐릭터만 바뀌고 바에는 옛 색이 남았다).
- 서브 화면(꾸미기·도감·대화)은 **캔버스 레이어를 올린다**(layer 5). 같은 레이어면 그리는 순서는 위여도 입력은 먼저 만들어진 가방 화면이 먹어서, 색 견본을 탭했는데 가방의 판매 버튼이 눌렸다(실측: 벨이 늘었다).
- 머리는 색이 아니라 형태이므로 이름으로 보여준다(짧은 머리·양갈래·모자…).

### 토큰 이전

토큰이 곧 신원이다(`docs/protocol.md` §1) — 저장소를 지우면 캐릭터를 잃고, 토큰을 옮기면 다른 기기에서 같은 캐릭터로 접속할 수 있다. 그래서 이 절의 목적은 두 가지다: **잃지 않게 적어 둘 수 있게 하는 것**과 옮겨 오는 것.

- 토큰은 **가려서** 보여준다(`a1b2c3…f9d0`). `[전체 보기]`로 펼치고 `[복사]`는 클립보드에 넣는다. 클립보드는 권한·비보안 컨텍스트에서 실패하므로, 복사를 누르면 **동시에 전체를 펼쳐** 눈으로 읽어 적을 수 있게 한다.
- 불러오기는 **파괴적 동작이라 2단 확인**이다: 첫 누름은 버튼 문구를 "정말 불러오기?"로 바꾸고 경고만 띄우고, 두 번째 누름에서 실행한다.
- 거절되면(형식 오류·같은 토큰) **2단 확인을 처음 상태로 되돌리고 이유를 화면 안 라벨로 보여준다**. 그러지 않으면 다음 붙여넣기가 한 번 누름으로 실행되고, 버튼은 "불러오기"인데 안내에는 "정말 …사라집니다"가 남아 확인 대기 중처럼 읽힌다. 모달은 layer 5이므로 HUD 토스트는 그 뒤에 가려 읽히지 않는다.
- 실행하면 슬롯의 토큰을 바꾸고 **위치·가방·벨·외형을 비운 뒤 장면을 다시 연다**. 위치는 `_persist(false)`로 비워야 한다 — 저장이 기본적으로 현재 좌표를 다시 써서 새 토큰이 옛 자리에서 시작하고, 서버 연결이 실패하면 계속 그 상태로 남는다. 이때 꾸미기 화면은 **확정 없이** 닫아야 한다 — 평소 닫기는 바뀐 외형을 서버로 보내므로, 새 토큰 슬롯에 옛 외형이 저장되고 옛 소켓으로 전송된다. 서버가 그 값의 단일 출처이므로 남겨 두면 옛 캐릭터의 값이 잠깐 보이고 서버 응답으로 덮인다(둘이 갈리는 것처럼 보인다). 부분적으로 갈아끼우지 않고 장면을 다시 여는 이유도 같다 — 어디까지 옛 캐릭터인지 알기 어렵다.
- 형식(UUID)은 클라이언트가 먼저 걸러 낸다. 같은 토큰이면 아무것도 하지 않는다.
- **벨 복제는 생기지 않는다**: 벨·가방은 서버가 토큰별로 소유하므로 같은 토큰을 두 기기에서 쓰면 같은 지갑을 공유하고(복제가 아니라 공유), 동시 접속은 서버가 옛 소켓을 끊는다.

### 회귀 판정

- 서버 유닛 5종: 선택지가 프리셋에서 유도되는지, 목록 밖 값 거절(가방 불변), 저장 + 스냅샷 반영, 간격 제한과 실패 시 예산 미소모, 재시작 후 유지.
- 브라우저 2탭(`npm run test:multiplayer`): **화면에 반영됐는지**로 판정한다 — 내 스프라이트가 즉시 바뀌는지(`myLook` 훅), 서버를 거쳐 B의 A 스프라이트 색이 바뀌는지(`remoteLook` 훅), 잘못된 토큰으로는 캐릭터가 바뀌지 않는지. 서버 방송만 보면 재적용을 빼먹어도 통과한다(실제로 그랬다). `remoteLook`은 **남의 캐릭터 전부**를 담되 **토큰은 넣지 않는다** — 하나만 고르면 외형을 바꾸지 않는 관찰자 소켓이 먼저 잡혀 "안 바뀐다"로 읽히고, 구분자로 토큰 앞자리를 쓰면 배포 웹 빌드에서도 켜져 있는 훅이 남의 신원 조각을 JS 전역에 올린다(자기 토큰조차 가려서 보여주는 정책과 어긋난다).
- 훅은 **값이 바뀔 때 게시**해야 한다. `_publish_test_points()`는 기동 때 한 번만 도는 함수라, 거기에만 넣었더니 초기값이 영원히 남아 스프라이트는 바뀌는데 테스트는 실패했다.

## 7. 캐릭터와 슬롯

- 슬롯은 **기기별 5칸**(`SaveManager.SLOT_COUNT`)이다. 한 기기에서 캐릭터 5명을 각각 키울 수 있고, 다른 기기에서 같은 외형·같은 이름을 쓰는 것도 허용한다(슬롯이 기기별이므로 막을 근거가 없다).
- 외형 프리셋은 `data/characters.json`(여3·남2)이며 항목을 추가하면 선택 화면이 자동으로 늘어난다. `gender`는 실루엣에만 반영되고 능력 차이는 없다.
- **이름 삭제 = 캐릭터 버리기**다. 슬롯을 비우면 토큰도 사라져 서버 기록과의 연결이 끊긴다 — 선택 화면이 삭제 전에 그 사실을 경고한다.
- 이름·외형·위치·벨·가방은 슬롯이 기억한다. 위치는 서버에도 저장되며 접속 시 서버 값이 우선이다.
