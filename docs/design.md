# Animals Farm — 게임 설계 문서

## 0. 한 줄 정의

닌텐도 스위치 **『동물의 숲』을 모티브로 한 브라우저 게임**. Godot 4(GDScript) + 웹(HTML5) export로 만들고, 사용자 소유 서버에서 정적 서빙한다.

- 확정: 엔진/언어(Godot 4, GDScript), 배포 형태(웹), 모티브(동물의 숲), 배포 파이프라인(`docs/deploy.md`)
- 진행 중: 코어 루프의 최소 1사이클 프로토타입(`scripts/main.gd` — 채집 → 가방 → 판매 → 자동 저장)
- 미확정: 이웃 동물 AI/대화, 집·마을 꾸미기, 도감, 멀티플레이 여부, 아트 톤&매너

원작을 그대로 복제하는 것이 목표가 아니다. 원작의 IP 자산(캐릭터·이름·에셋·음악)은 사용하지 않고, **차용하는 것은 게임 구조(느린 실시간 루프, 수집, 꾸미기, 이웃과의 관계)뿐**이다.

## 1. 코어 루프

원작의 핵심은 "짧게 접속해도 매일 조금씩 달라져 있는 마을"이다. 그래서 루프의 단위는 세션이 아니라 **하루**다.

1. **접속** — 현실 시간이 곧 게임 시간(`scripts/game_clock.gd`). 현재는 계절·시각이 **HUD 표시에만** 쓰인다 — 계절/시각에 따른 스폰 변화는 *미구현*.
2. **일일 갱신** — 마지막 접속 이후 하루가 지났으면 채집물이 전부 되살아난다(`GameClock.days_since`). 일일 이벤트 시스템은 *미구현*.
3. **채집** — 나무·조개·잡초 등을 모은다(`scripts/gatherable.gd`, 배치는 `data/gatherables.json`).
4. **환금** — 모은 것을 팔아 벨(재화)을 얻는다(가격은 `data/items.json`이 유일한 출처).
5. **투자** — 벨을 집·마을 꾸미기와 도구 확장에 쓴다 *(미구현 — 다음 단계)*.
6. **관계** — 이웃 동물의 의뢰를 받고 친밀도를 올린다 *(미구현 — 다음 단계)*.

**설계 원칙**: 접속 1회에 할 일을 다 못 끝내게 만들지 않는다. 하루치 콘텐츠는 5~10분에 소진되어야 하고, 남은 것은 "내일"로 넘긴다. 이 원칙에 기여하지 않는 기능은 제안 단계에서 잘라낸다(`docs/agents/roles.md` GameDesigner).

### 2.1 2.5D 화면 구성

"2D와 3D가 섞인" 룩을 다음 세 층으로 만든다.

| 층 | 무엇 | 구현 |
|---|---|---|
| 3D 월드 | 섬(두께 있는 박스) · 모래 테두리 · 바다 · 나무(원기둥+구) · 조개 · 잡초 | `main.gd::_build_environment`, `gatherable.gd` — 전부 Godot 프리미티브 메시. 방향광 그림자가 있어 입체로 읽힌다 |
| 2D 캐릭터 | 플레이어 (32×40 픽셀 스프라이트, 4방향 × 걷기 6프레임 10FPS + idle) | `player_sprite.gd` — `AnimatedSprite3D` 빌보드. 프레임은 **런타임에 픽셀로 생성**(외부 아트 에셋 0개), 좌측은 우측 프레임을 반전해 재사용 |
| 2D UI | 시계·벨·가방·조작 안내·토스트 | `main.gd::_build_hud`가 `CanvasLayer` + 빈 `Label`을 만들고, 문구 조립은 `main.gd::_refresh_hud`가 한다(고칠 때 두 함수를 함께 볼 것) |

카메라는 **직교 투영**(`PROJECTION_ORTHOGONAL`, size 9.5)에 pitch -38°, yaw 0°이고 플레이어를 부드럽게 따라간다. yaw를 0으로 고정한 이유는 화면 위쪽이 월드 -Z와 일치해 입력 매핑이 단순해지기 때문이다 — 카메라를 회전시키면 `player.gd`의 입력→월드 변환도 같이 고쳐야 한다.

빌보드 캐릭터에서 실측으로 걸린 함정 세 가지(2026-09-04, 브라우저):
- 완전 빌보드(`BILLBOARD_ENABLED`)는 카메라 피치까지 따라가 캐릭터가 뒤로 누운 것처럼 보인다 → `BILLBOARD_FIXED_Y`
- 노드 원점이 스프라이트 중앙이면 배치가 어긋난다 → `offset`으로 원점을 발바닥에 맞춤
- 빌보드가 방향광 그림자를 드리우면 공중에 뜬 얼룩처럼 보인다 → 스프라이트 그림자는 끄고, 발밑에 타원 데칼을 따로 깐다(`player.gd::_add_ground_shadow`)

`player_sprite.gd`는 **Gemini CLI(`agy`)가 구현**했다 — 걷기 사이클처럼 결과를 눈으로 판정하는 작업을 다른 모델에 맡기고, 이 세션은 계약(애니메이션 이름 8개, `set_move_dir`/`facing` API, 웹 제약)과 검증(헤드리스 + 브라우저 스모크)을 담당했다(`docs/agents/roles.md` §3).

## 3. 밸런스·경제 데이터 규칙

같은 원칙이 색에도 적용된다: 수치는 `data/items.json`·`data/gatherables.json`, 색은 `data/palette.json`이 단일 출처이며 코드는 읽어 쓰기만 한다(`Balance`, `Palette`).

- 수치는 코드에 흩뿌리지 않고 `data/*.json`에만 둔다. 유효범위도 **주석이 아니라 구조화된 필드**로 데이터에 둔다 — `items.json`은 항목별 `price_range`, `gatherables.json`은 최상위 `limits`(예: `respawn_sec: [10, 86400]`)가 단일 출처다. 코드에 범위를 하드코딩하면 이 규칙이 깨진다(2026-09-03 Codex 감사 지적으로 `gatherable.gd`의 하드코딩 범위를 제거).
- 코드는 데이터를 읽을 때 유효범위로 **항상 클램프하고 항상 경고를 남긴다**. 이 규칙은 `scripts/balance.gd`(`Balance.clamp_value`)가 단독 소유하며 가격·리스폰 양쪽이 같은 코드를 쓴다. 범위가 없거나 `[lo, hi]` 형식이 아니거나 `lo > hi`면 폴백 범위를 적용하고 경고한다 — 폴백은 **출처가 아니라 데이터가 깨졌을 때의 마지막 안전장치**다.
- `data/items.json`에 없는 아이템은 0벨로 조용히 처리하지 않는다(판매 시 가방에서 사라져 플레이어 손실이 된다) — 판매 대상에서 제외하고 가방에 남기며 경고한다.
- 밸런스 변경은 `data/` 파일만 바뀌어 코드 확장자가 없는 커밋이 되기 쉬운데, pre-commit 게이트는 `.json`도 리뷰 대상에 포함한다(`scripts/review.js`의 diff 필터).

## 4. 세이브 데이터 스키마

```jsonc
{ "version": 1, "bells": 0, "inventory": { "wood": 3 },
  "first_played_unix": 0, "last_played_unix": 0 }
```

- `version` 필드는 필수. 마이그레이션은 `SaveManager.migrate()` 한 곳에서만 하고, **각 단계마다 손실 여부를 주석으로 명시**한다.
- 미래 버전 세이브(다운그레이드)는 마이그레이션하지 않고 `_read_only`로 잠근다 — 신버전에서 만든 데이터를 구버전이 덮어써 잃는 사고를 막는다.
- 손상된 세이브는 조용히 덮어쓰지 않고 `save.json.corrupt`로 백업한 뒤 새로 시작한다.
- v0(버전 필드 없는 세이브) → v1 마이그레이션은 누락 필드를 전부 채운다. `first_played_unix`는 복구 불가능한 정보라 현재 시각으로 채우고 그 사실을 경고로 남긴다.
- **회귀 테스트**: `tests/test_save_migration.gd`(v0→v1 필드/값 보존, 미래 버전 읽기 전용, 손상 세이브 폴백). `./scripts/verify-project.sh`가 실행한다 — 표준 Godot 빌드가 필요하다.
- **스키마 변경 절차**(`docs/agents/roles.md` §4): TechAnalyst+QAEngineer 페르소나 검토 → 3종 CLI 교차검증(`npm run panel`) → 구버전 세이브 로드 회귀 테스트. 진행도 손실은 되돌릴 수 없다.

## 5. 비주얼 가이드라인

전체 가이드라인은 아직 미확정이지만, **캐릭터 층은 코드에 확정됐다**(2026-09-04). "그레이박스(도형만)" 서술은 더 이상 정확하지 않으므로 확정된 것과 아닌 것을 나눠 적는다.

### 확정된 것

| 항목 | 값 | 단일 출처 |
|---|---|---|
| 폰트 | Noto Sans KR(OFL) 임베드 — 웹은 시스템 폰트 폴백이 없어 한글이 두부(□)가 된다 | `project.godot`의 `gui/theme/custom_font` |
| 캐릭터 스프라이트 규격 | 32×40 px, `pixel_size` 0.05 → 월드 1.6×2.0, 원점=발바닥 | `scripts/player_sprite.gd` 상단 const |
| 화면 색 전체(월드·UI·캐릭터) | 하늘/바다/섬/모래/나무/조개/잡초/그림자, HUD 글자·외곽선, 캐릭터 피부·셔츠·바지·신발·눈 | **`data/palette.json`** — `Palette.color(group, key)`로만 읽는다 |
| 걷기 애니메이션 원칙 | 4방향 × 6프레임 10FPS, 다리 교차 4~5px, 팔은 반대 위상 3px, 몸 bob 2px(접지 프레임이 최저점) | `scripts/player_sprite.gd` |

색 하나를 바꾸려면 `data/palette.json`만 고치면 된다. `tests/test_palette.gd`가 **`scripts/*.gd`를 스캔해 실제 호출된 `Palette.color(group, key)`를 추출**해 데이터와 대조하므로(키 목록을 테스트에 다시 적지 않는다), 코드가 없는 키를 참조하면 커밋 전에 걸린다. 팔레트에 없는 키를 요청하면 **마젠타(#ff00ff)로 그려지고 경고가 남는다** — 화면에 마젠타가 보이면 키 누락이라는 뜻이므로, 조용히 검은색으로 대체해 눈치채지 못하는 상황을 피한다.

### 미확정인 것

- 타일/오브젝트 스케일 규격, 애니메이션 원칙의 나머지(히트스톱 등), 아트 톤&매너.
- 팔레트는 "현재 색이 무엇인지"의 단일 출처일 뿐, "왜 그 색인지"(톤&매너)는 아직 문서화되지 않았다.

### `agy` 비주얼 패리티 리뷰의 현재 상태: **부분 활성**

- 캐릭터 스프라이트는 이미 `agy`가 구현하고 3라운드 피드백(빌보드 축 → 발바닥 원점/그림자 → 사이클 과장)으로 다듬었다(`docs/agents/roles.md` §3).
- 위 "미확정인 것"의 월드/UI 팔레트가 문서화되면 **전체 화면에 대한 필수 게이트로 승격**한다. 그때까지는 캐릭터 층에 한해 활용한다.

## 6. 조작

| 입력 | 동작 |
|---|---|
| **마우스 클릭 / 화면 탭** | **그 지점으로 이동. 나무·놓인 물건·다른 캐릭터를 누르면 다가가서 자동 처리** |
| 방향키 | 이동(누르는 순간 클릭 목표는 취소됨) |
| Space / Enter (`ui_accept`) | 주변에 놓인 물건이 있으면 줍고, 없으면 채집 |
| S | 가방 전부 판매 |
| T | 채팅 입력 열기 (Enter 전송, Esc 취소) |
| Q | 가방에서 1개를 발밑에 놓기 |
| 1 ~ N | 감정 표현 이모티콘 (`data/emotes.json` 순서, 개수는 데이터가 정한다) |

Godot 기본 입력맵(`ui_*`)과 직접 키코드만 사용해 커스텀 입력맵 없이 동작한다. 채팅 입력 중과 시트가 열린 동안에는 게임 조작을 받지 않는다 — 그러지 않으면 "s"를 치는 순간 물건이 팔리고, 시트 뒤에서 캐릭터가 움직인다.

### 터치 조작 (폰 브라우저)

`DisplayServer.is_touchscreen_available()`이 참이면 터치 UI가 뜬다. 설계 근거는 `docs/meetings/2026-09-04-1150-폰-터치-조작-설계.md`.

| 입력 | 동작 |
|---|---|
| 화면(월드) 탭 | 그 지점으로 이동. **대상을 탭하면 사거리까지 다가가 자동 채집/줍기**, 다른 캐릭터는 대화 거리까지 |
| 왼쪽 아래 영역을 누른 채 끌기 | **플로팅 가상 조이스틱** — 누른 지점이 중심이 되고, 기울인 만큼 천천히/빠르게 걷는다 |
| 우하단 큰 버튼 "채집" | 줍기/채집(키보드 Space와 동일) |
| "채팅" 버튼 | 입력창 열기 |
| "감정" 버튼 | 이모티콘 하단 시트(칸 수는 `data/emotes.json`이 정한다) |
| "버림" 버튼 | 가방에서 1개 놓기 |
| HUD 가방 줄 탭 | 판매 확인 시트 → 확정 시 전부 판매 |

**판매 버튼을 두지 않은 이유**: 되돌릴 수 없는 동작이라 오조작 한 번에 수집품이 사라진다. 그래서 상시 버튼 대신 가방 줄 → 확인 시트를 거친다.

### 탭-투-무브(대상 지향) 설계 근거

검토 결과는 `docs/meetings/2026-09-04-1150-폰-터치-조작-설계.md` §11.

- **조이스틱을 대체하지 않고 병행**한다. 짧은 미세 이동과 산책 감각은 아날로그가 낫고, 원거리 이동·목표 지향은 탭이 낫다.
- 단순히 "그 좌표로 걷기"가 아니라 **탭한 대상에 맞춰 동작**한다: 채집물 → 사거리(1.6)보다 조금 안쪽(1.1)까지 접근 후 자동 채집, 놓인 물건 → 접근 후 자동 줍기, 다른 캐릭터 → 대화 거리까지. 폰에서 가장 번거로운 "나무 옆 정확한 자리에 서기"가 이 방식으로 사라진다.
- 탭 판정 반경은 1.3 유닛(손가락이 뭉툭한 것과 옆 나무를 잘못 집는 것 사이의 타협).
- **수동 입력(방향키·조이스틱)이 들어오면 목표를 즉시 버린다** — 손으로 조작하는 중 캐릭터가 예전 목표로 끌려가면 조작을 빼앗긴 느낌이 된다.
- 목표 지점에는 바닥 마커를 표시한다. 없으면 "눌렀는데 반응이 없다"고 느낀다.
- 조이스틱 영역(좌하단)의 터치는 이동 지시로 해석하지 않는다.
- **아직 충돌체가 없어서 직선 이동으로 충분하다**(나무도 통과 가능). 장애물을 넣는 시점에 내비게이션이 필요해진다 — 이 비용이 여기 잠재해 있다.
- 정밀 배치(꾸미기 P6에서 가구 놓기)는 탭 이동으로 안 된다. 그때 별도 UI가 필요하다.

**키보드와 터치는 병행**한다. 두 입력을 합산하지 않고 **크기가 큰 쪽**을 쓴다 — 합산하면 둘을 같이 쓸 때 속도가 두 배가 된다.

### 좁은 화면 대응

- HUD는 **앵커/마진 기반**이다. 절대좌표를 쓰던 시절에는 폰 세로(412×839)에서 접속 상태 라벨이 화면 밖으로 잘렸다.
- 화면 폭이 700px 미만이면 채팅 로그를 6줄 → 3줄로 줄이고 화면 아래쪽으로 옮긴다(캐릭터를 가리지 않게).
- 조작 안내 문구는 터치/키보드에 맞춰 다르게 나온다 — 폰에서 "[방향키] 이동"은 오히려 터치 UI를 못 찾게 만든다.
- 직교 카메라 `size`는 세로 기준이라 세로 모드에서 가로 시야가 급격히 좁아진다. 기준 비율(16:9)보다 좁아진 만큼 `size`를 키우고(최대 1.8배) 화면 회전 시 다시 계산한다.
- 터치 환경에서는 방향광 그림자를 끈다(WebGL2에서 발열·프레임 드랍의 주 원인). 캐릭터 접지감은 발밑 타원 데칼이 담당하므로 유지된다.

### 채팅 입력 방식

웹에서는 **캔버스 위에 실제 DOM `<input>`을 얹는다**(`scripts/chat_input.gd`). Godot의 `experimental_virtual_keyboard`를 쓰지 않는 이유는 모바일 브라우저에서 **한글 IME 조합이 풀리거나 글자가 중복 입력되는** 사례가 보고돼 있기 때문이다(회의 §9-나). DOM 입력은 브라우저 네이티브라 OS 키보드·IME와 그대로 연동되고, IME 조합 중의 Enter(`isComposing`)는 전송으로 취급하지 않는다.

웹이 아닌 환경(에디터/데스크톱)에서는 같은 파일이 Godot `LineEdit`으로 갈라진다.

## 7. 캐릭터와 슬롯

- 슬롯은 **기기별 5칸**(`SaveManager.SLOT_COUNT`)이다. 한 기기에서 캐릭터 5명을 각각 키울 수 있고, 다른 기기에서 같은 외형·같은 이름을 쓰는 것도 허용한다(슬롯이 기기별이므로 막을 근거가 없다).
- 외형 프리셋은 `data/characters.json`(여3·남2)이며 항목을 추가하면 선택 화면이 자동으로 늘어난다. `gender`는 실루엣에만 반영되고 능력 차이는 없다.
- **이름 삭제 = 캐릭터 버리기**다. 슬롯을 비우면 토큰도 사라져 서버 기록과의 연결이 끊긴다 — 선택 화면이 삭제 전에 그 사실을 경고한다.
- 이름·외형·위치·벨·가방은 슬롯이 기억한다. 위치는 서버에도 저장되며 접속 시 서버 값이 우선이다.
